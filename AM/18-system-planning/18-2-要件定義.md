# 18-2 要件定義

システムに**何を求めるかを確定する**工程を扱う。

[12-1 システム・ソフトウェア要件定義](../12-system-development/12-1-システム-ソフトウェア-要件定義.md) が技法（DFD、決定表、ユースケース図）を中心に扱うのに対し、本章は**企画・調達の観点**から要件定義を見る。誰が責任をもつのか、どういう契約形態が適切か、要件の追跡をどう確保するかが論点になる。

## 1. 機能要件と非機能要件

> **非機能要件に該当するもの**はどれか。

答えは、

> **ソフトウェアの信頼性、効率性など品質に関する要件。**

要件の階層を整理する。

| 要件 | 内容 |
| --- | --- |
| **業務要件** | **新しい業務の在り方をまとめた上で、業務上実現すべき要件**／**業務の手順や入出力情報、ルールや制約などの要件** |
| **機能要件** | **業務要件を実現するために必要なシステムの機能に関する要件** |
| **非機能要件** | **信頼性、効率性など品質に関する要件** |

**機能要件が「何ができるか」、非機能要件が「どの程度の品質で動くか」**という区別である。

非機能要件に含まれる主な項目を挙げる。

| 分類 | 例 |
| --- | --- |
| 可用性 | 稼働率、障害時の復旧時間（→ [4-2 システムの評価指標](../04-system-components/4-2-システムの評価指標.md)） |
| 性能・拡張性 | 応答時間、スループット、将来の拡張 |
| 運用・保守性 | 運用時間、バックアップ、監視 |
| 移行性 | 移行方式、移行期間（→ [12-5 導入・受入れ支援](../12-system-development/12-5-導入-受け入れ支援.md)） |
| セキュリティ | 認証、アクセス制御、ログ（→ [11-4 情報セキュリティ対策](../11-security/11-4-情報セキュリティ対策.md)） |
| システム環境・エコロジー | 設置環境、消費電力 |

**非機能要件が軽視されやすい**のには理由がある。機能要件は利用者が自分の言葉で語れるが、非機能要件は「速いほうがいい」「止まらないほうがいい」としか言えないことが多い。しかし曖昧なまま進めば、完成後に「遅すぎて使えない」という事態になる。**数値で合意しておく**ことが、この工程の要点になる。

品質特性の分類そのものは [12-1 システム・ソフトウェア要件定義](../12-system-development/12-1-システム-ソフトウェア-要件定義.md) で扱う。

> **出題** 非機能要件: H24午前I問24

## 2. 要件定義工程の契約形態

> 「情報システム・モデル取引・契約書」によれば、**要件定義工程**を実施する際に、ユーザ企業がベンダと締結する**契約の形態**について適切なものはどれか。

答えは、

> **構築するシステムがどのような機能となるか明確になっていないので準委任契約にした。**

**要件定義は準委任契約が適切**とされる。理由は論理的である。

| 契約形態 | 性質 | 要件定義に適するか |
| --- | --- | --- |
| **請負契約** | **仕事の完成**に対して対価を支払う。受注者が完成責任を負う | **適さない**。何を完成させるかが未確定だから |
| **準委任契約** | **業務の遂行**に対して対価を支払う。完成責任は負わない | **適する** |

**「何を作るかを決める工程」で「完成責任」を課すのは論理的に成立しない**。完成の定義ができないからである。仮に請負にすれば、受注者はリスクを価格に転嫁するか、曖昧な範囲で合意して後から紛争になる。

誤答として並ぶ記述を確認する。

| 記述 | なぜ誤りか |
| --- | --- |
| **仕様の決定権はユーザ側ではなくベンダ側にある**ので準委任契約にした | **仕様の決定権はユーザ側にある**。要件を決めるのはユーザの責任である |
| ベンダに委託する作業の成果物が具体的に想定できないので**請負契約**にした | 成果物が想定できないなら**準委任**が適切。請負は成果物が定義できることが前提 |
| ユーザ内のステークホルダとの調整を行う責任が曖昧にならないように**請負契約**にした | **ユーザ内の調整はユーザの責任**であり、契約形態で解決する問題ではない |

**要件定義におけるユーザの責任**が、この設問の裏のテーマである。「ベンダに任せれば要件を決めてくれる」という期待は成り立たない。ベンダは支援はできるが、**自社の業務をどうするかを決められるのはユーザだけ**である。

契約形態と工程の対応は [18-3 調達計画及び実施](18-3-調達計画及び実施.md) で詳しく扱う。

> **出題** 要件定義工程の責任分担: H28午前I問25

## 3. トレーサビリティ

> システム要件定義プロセスにおいて、**トレーサビリティが確保されている**ことを説明した記述として、適切なものはどれか。

答えは、

> **利害関係者の要求の根拠と成果物の相互関係が文書化されており、開発の途中で生じる仕様変更をシステムに求められる品質に立ち返って検証できる。**

**トレーサビリティ（追跡可能性）とは、要求と成果物の対応関係を追えること**である。

確保されていると何ができるか。

- **上流から下流へ**：ある要求が、どの設計・どのコード・どのテストに反映されたかを追える
- **下流から上流へ**：ある機能が、どの要求に基づくものかを追える

これが効くのは**変更が起きたとき**である。「この要求を変えたい」となったとき、影響範囲が即座に分かる。逆に「この機能は本当に必要か」という問いにも、根拠となる要求をたどって答えられる。**「なぜそうなっているか」を失わないための仕組み**だといえる。

誤答として並ぶ記述を確認する。

| 記述 | 実際は何か |
| --- | --- |
| 移行マニュアルや運用マニュアルが完成しており、業務の実施方法を利用者が確認できる | 文書化の完了であり、追跡可能性ではない |
| 外注部分が決定され、調達先が選定・契約されており、**容易に変更できない** | 調達の確定。**むしろ柔軟性を失っている** |
| モジュールの相互依存関係が確定しており、以降の工程で**個別モジュールの仕様を変更できない** | **変更できないことは利点ではない** |
| **要求の根拠と成果物の相互関係が文書化されており、仕様変更を品質に立ち返って検証できる** | **トレーサビリティ** |

**「変更できない」ことを利点として書いた選択肢は誤り**である。トレーサビリティの価値は、変更を禁じることではなく、**変更の影響を正しく評価できるようにする**ことにある。

同じ考え方は [13-4 構成管理・変更管理](../13-software-development-management/13-4-構成管理-変更管理.md) の構成管理にも現れる。「いま何がどうなっているか」が分からなければ、変更の判断もできない。

> **出題** 要件定義とトレーサビリティ: R5午前I問24

## この章のまとめ

- **業務要件（業務の在り方）→ 機能要件（システムの機能）→ 非機能要件（品質）**という階層。**非機能要件は数値で合意する**ことが要点。
- **要件定義には準委任契約が適する**。何を作るかが未確定な工程に完成責任を課すのは成立しない。
- **仕様の決定権とステークホルダの調整責任はユーザ側にある**。契約形態で肩代わりできるものではない。
- **トレーサビリティは要求と成果物の対応を追えること**。価値は変更を禁じることではなく、**変更の影響を正しく評価できる**ことにある。
