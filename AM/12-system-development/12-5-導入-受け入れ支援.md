# 12-5 導入・受入れ支援

完成したシステムを**実際の業務で使える状態にする**工程を扱う。

開発が終わってもシステムは使えない。既存システムからデータを移し、利用者に使い方を教え、旧システムと切り替える──この一連の作業が導入である。そしてここには、開発工程とは質の違うリスクがある。**失敗したときに止まるのが「開発」ではなく「業務」**だという点である。だから導入方式の選択は、**問題が起きたときの影響をどこまで局所化できるか**を基準に判断する。

午前Iの問20前後から出題されるが、16年で1問と出題は少ない。

出題が少ない分野のため、本章では過去問で問われた移行方式に加えて、導入工程全体の整理を補っている。

## 1. 導入工程の作業

| 作業 | 内容 |
| --- | --- |
| 導入計画の作成 | 移行の手順、日程、体制、中止判断の基準を定める |
| 環境の構築 | 本番環境のハードウェア・ソフトウェアを準備する（→ [13-3 開発環境管理](../13-software-development-management/13-3-開発環境管理.md)） |
| データ移行 | 旧システムのデータを新システムの形式に変換して投入する |
| 利用者教育 | 操作方法・業務手順を教える |
| 運用テスト（受入れテスト） | 実際の業務環境で利用者が最終確認を行う |
| 切替え | 旧システムから新システムへ移行する |

導入計画でとりわけ重要なのが、**切り戻し（ロールバック）の手順と、中止を決める判断基準**を事前に定めておくことである。移行当日に想定外の問題が起きたとき、「もう少し頑張れば動くかもしれない」と粘った結果、戻すこともできなくなる──これが最悪の事態である。**どの時刻までに何が達成できていなければ中止するか**を数値で決めておく必要がある。

## 2. システムの移行方式

旧システムから新システムへの切替え方には、いくつかの方式がある。**どの軸で段階的に進めるか**で分類すると整理できる。

| 方式 | 進め方 | 特徴 |
| --- | --- | --- |
| **一斉移行（ビッグバン移行）** | 全部門・全機能を一度に切り替える | **他の移行方式に比べると移行期間は短くできるが、事前に全部門との間で詳細な計画を立てるとともに、新システムに高い信頼性が要求される** |
| **パイロット移行** | **部門（組織）**を限定して先行導入する | **限定した部門で新システムを導入・観察した後に他の全部門を移行するので、移行に関する問題が発生しても影響範囲を局所化できる** |
| **段階移行（順次移行）** | **機能（サブシステム）**を限定して順次移行する | **機能的に閉じたサブシステム単位に短期間で順次移行していくので、運用部門の負荷が少なく、問題が発生しても当該サブシステム内に抑えることができる** |
| **並行運用** | 新旧両システムを**同時に動かす** | **新・旧両システム分のリソースを用意し並行稼働させるので、新システムで問題が発生しても業務への影響を最小にできる** |

**パイロット移行と段階移行の違いは、何を限定するか**である。

- **パイロット移行は「部門」を限定する**。1つの支店だけで新システムを使い、問題がなければ全支店に展開する。
- **段階移行は「機能」を限定する**。受注機能だけを新システムに切り替え、在庫機能は旧システムのまま、というように進める。

```
パイロット移行：  [A支店] 新 │ [B支店] 旧 │ [C支店] 旧   → 順次新へ
段階移行：        [受注] 新 │ [在庫] 旧 │ [会計] 旧     → 順次新へ
```

**並行運用**は最も安全だが、**新旧両方のリソースと、両方にデータを入力する二重作業**が発生するため、コストと現場の負担が大きい。金融機関の勘定系のように絶対に止められないシステムで採用される。

**一斉移行**は期間が短くコストも抑えられるが、**失敗したときに逃げ場がない**。したがって新システムの信頼性と、全部門を巻き込んだ綿密な計画が前提条件になる。

どの方式も**「安全性」と「期間・コスト」のトレードオフ**であり、システムが止まったときの業務影響の大きさ（→ [4-1 システムの構成](../04-system-components/4-1-システムの構成.md) のミッションクリティカルシステム）に応じて選択する。

> **出題** パイロット移行方式: H21午前I問20

## 3. 受入れテストと教育

### 3.1 運用テスト（受入れテスト）

開発側が行うシステムテストと異なり、**運用テストは利用者側が、実際の業務環境で、実際の業務データを使って**行う。確認するのは「仕様どおりに動くか」ではなく、**「業務が回るか」**である。

- 業務の流れに沿って一連の処理が完結するか
- 繁忙期の処理量に耐えられるか
- 例外的な業務（締め処理、訂正処理）が扱えるか
- 運用手順書どおりに運用できるか

仕様を満たしていても業務が回らないことはある。たとえば1件あたり3秒の応答時間は仕様上問題なくても、1日1,000件を手入力する現場では致命的になりうる。こうした齟齬を稼働前に見つけるのが運用テストの役割である。

### 3.2 利用者教育

教育の対象は**エンドユーザ**だけでなく、**運用担当者**にも及ぶ。操作マニュアル、運用手順書、障害時の連絡体制を整備し、研修を実施する。

導入直後は問い合わせが集中するため、**サービスデスクの体制を事前に強化しておく**ことも導入計画の一部になる（→ [15-4 サービスの運用](../15-service-management/15-4-サービスの運用.md)）。

## この章のまとめ

- 移行方式は**何を限定するか**で区別する。**パイロット移行は部門を限定、段階移行は機能を限定、並行運用は新旧を同時稼働、一斉移行は一度に全部**。
- **パイロット移行の利点は影響範囲の局所化**。**一斉移行は期間が短い代わりに高い信頼性と綿密な計画が要る**。
- 方式の選択は**安全性と期間・コストのトレードオフ**であり、業務が止まったときの影響の大きさで決める。
- **運用テストは「仕様どおりか」ではなく「業務が回るか」**を利用者が実環境で確認する工程である。
