# 12-3 実装・構築

設計をもとに**実際にプログラムを書き、動く形にする**工程を扱う。

この工程で問われるのは「どう書くか」よりも、**書いたものが正しいことをどう確かめるか**である。テストは [12-4 統合・テスト](12-4-統合-テスト.md) で扱うので、本章ではテストより前の段階──コーディング中・実行中に誤りを捕まえる手段を中心に見ていく。

出題が少ない分野のため、本章では過去問で問われた内容に加えて、デバッグ技法の整理を補っている。

## 1. プログラミングの進め方

実装工程では、設計書に従ってコードを書き、単体で動作を確かめる。

| 作業 | 内容 |
| --- | --- |
| コーディング | 設計に基づいてソースコードを記述する |
| コーディング標準の遵守 | 命名規則、インデント、禁止構文などを統一する |
| 静的解析 | 実行せずにソースコードを解析し、規約違反や潜在的な不具合を検出する |
| コードレビュー | 他者がソースコードを検証する（→ [12-2 設計](12-2-設計.md)） |
| 単体テスト | モジュール単位で動作を確認する（→ [12-4](12-4-統合-テスト.md)） |

**コーディング標準**が重視されるのは、読みやすさのためだけではない。書き方が統一されていれば、**静的解析ツールで機械的に検査できる**ようになり、レビューでは本質的な論理の検討に集中できる。「人が目で見て直すべきこと」と「機械に任せられること」を分けるのが標準化の実利である。

## 2. アサーションチェック

> **プログラム実行中の特定の時点で成立する変数間の関係や条件を記述した論理式を埋め込んで、そのプログラムの正当性を検証する手法を、アサーションチェックという。**

埋め込む論理式を**表明（assertion）**という。「この時点で変数 $x$ は必ず正の値である」「配列の添字は0以上かつ上限未満である」といった、**プログラマが「当然成り立つはずだ」と考えている前提**を明示的にコードに書き込む。

```
// 例：除算の前に、分母がゼロでないことを表明する
assert(divisor != 0);
result = dividend / divisor;
```

実行時に表明が成り立たなければ、その場でプログラムを停止して知らせる。

この手法の価値は、**誤りを「発生した場所」で捕まえられる**点にある。表明がなければ、不正な値はそのまま計算を通り抜け、ずっと後の処理でおかしな結果として現れる。そこから原因を遡るのは骨が折れる。表明を置いておけば、**前提が崩れた瞬間に止まる**ので、原因箇所がそのまま判明する。

また表明は、**設計上の前提をコードに残す文書**としても働く。コメントは古くなっても誰も気づかないが、表明は前提が崩れれば実行時に知らせてくれるので、嘘をつかない。

誤答として並ぶ他の手法と区別する。

| 手法 | 内容 |
| --- | --- |
| **アサーションチェック** | **表明（論理式）を埋め込んで、実行時に前提が成り立つかを検証する** |
| コード追跡（トレース） | 実行経路や変数の変化を順に記録して追う |
| スナップショットダンプ | 指定した時点のメモリやレジスタの内容を出力する |
| テストカバレッジ分析 | テストがコードのどこまでを実行したかを測る（→ [12-4](12-4-統合-テスト.md)） |

**「論理式を埋め込む」のがアサーション**、「状態を記録・出力する」のがトレースやダンプ、「どこまで通ったかを測る」のがカバレッジ分析、という役割の違いで判別できる。

## 3. デバッグの技法

誤りを見つけて取り除く作業が**デバッグ**である。手段は「静的に調べる」か「動かして調べる」かに分かれる。

| 技法 | 内容 |
| --- | --- |
| 静的解析ツール | 実行せずにソースコードを解析し、未初期化変数や到達不能コードを検出する |
| デバッガ | ブレークポイントで実行を止め、変数の値を確認しながら1行ずつ実行する |
| トレーサ | 実行経路や変数の変化を記録する |
| スナップショットダンプ | 特定時点のメモリ内容を出力する |
| メモリダンプ | 異常終了時のメモリ全体を出力する |
| **アサーションチェック** | 表明を埋め込んで前提の成立を検証する |
| 逆アセンブラ | 機械語をアセンブリ言語に変換する |

デバッグを支援するこれらの道具は**開発ツール**として整理される（→ [5-4 開発ツール](../05-software/5-4-開発ツール.md)）。

実装工程で押さえておきたいのは、**誤りを早く見つけるほど修正コストが小さい**という原則である。コーディング中に静的解析で見つかる誤りは数分で直るが、同じ誤りがテスト工程で見つかれば再テストが要り、稼働後に見つかれば業務に影響が出る。アサーションも静的解析もコードレビューも、**検出のタイミングを少しでも前に倒す**ための投資だと理解すると、これらを導入する意味が一貫して見える。

## この章のまとめ

- **アサーションチェックは、成り立つはずの条件を論理式としてコードに埋め込み、実行時に検証する**手法。**誤りが発生したその場で止まる**ので原因の特定が速い。
- トレース（経路の記録）、スナップショットダンプ（時点の状態出力）、カバレッジ分析（実行範囲の測定）とは役割が異なる。
- 実装工程の技法はいずれも**誤りの検出を早い段階に前倒しする**ためにある。
