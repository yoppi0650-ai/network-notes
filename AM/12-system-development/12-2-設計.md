# 12-2 設計

[12-1](12-1-システム-ソフトウェア-要件定義.md) で決めた「何を作るか」を、「**どう作るか**」に落とし込む工程を扱う。

設計の良し悪しを測る基準は、突き詰めると**変更に強いかどうか**である。ソフトウェアは作って終わりではなく、業務の変化に合わせて何年も直し続ける。そのとき「1か所直したら別の10か所が壊れた」となるか、「1か所直せば済んだ」となるかは設計で決まる。本章で扱うモジュール分割（強度と結合度）、オブジェクト指向、アーキテクチャパターンは、いずれも**変更の影響範囲をどう閉じ込めるか**という同じ問題への回答である。

ネットワークスペシャリスト午前IIでは問24前後から、午前Iでは問16前後から出題される。16年で15問と、分野12のなかで最も出題が多い。

## 1. モジュール分割

プログラムを部品（モジュール）に分けるとき、**良い分割**と**悪い分割**がある。その良し悪しを測る2つのものさしが、モジュール強度とモジュール結合度である。

> **モジュール強度（結束性）は高いほど良い。モジュール結合度は低いほど良い。**

言い換えれば、**「1つのモジュールの中はまとまっていて、モジュールどうしのつながりは細い」**のが良い設計である。中がまとまっていれば、そのモジュールを理解するのに他を見なくて済む。つながりが細ければ、変更の影響が他に波及しにくい。

### 1.1 モジュール強度（結束性）

モジュール内の要素がどれだけ密接に関連しているかの尺度である。**弱いものから強い順**に並べる。

| 強度 | 内容 | 例 |
| --- | --- | --- |
| 暗号的強度（最弱） | 関連のない処理を単に寄せ集めた | — |
| **論理的強度** | 関連する複数の機能をまとめ、**引数で使い分ける** | **二つの機能A、Bは一部重複する部分が多いので一つにまとめ、使い分けるための引数を設けた** |
| **時間的強度** | **ある時点で一括して実行される処理**をまとめた | **複数の機能それぞれに必要な初期設定の操作が、ある時点で一括して実行できるので一つにまとめた** |
| 手順的強度 | 決まった順序で実行される処理をまとめた | — |
| **連絡的強度** | 順序があり、**かつデータの受渡しがある**処理をまとめた | **二つの機能A、Bは必ずこの順番に実行し、かつAで計算した結果をBで使うので一つにまとめた** |
| **情報的強度** | **同一のデータ構造を扱う複数の機能**をまとめ、データを外から隠した | **ある木構造データを扱う機能をそのデータとともに一つにまとめ、木構造データをモジュールの外から見えないようにした** |
| 機能的強度（最強） | 単一の機能だけを実現する | — |

**情報的強度**は、オブジェクト指向の**カプセル化**そのものである。データとそれを扱う操作を1つにまとめ、内部構造を外に見せない。こうしておけば、木構造の実装を配列からポインタに変えても、利用者側は一切影響を受けない。**変更の影響がモジュールの中に閉じる**ので強度が高いと評価される。

判別のコツは、**「なぜまとめたのか」の理由を読む**ことである。「重複しているから」は論理的強度、「同じタイミングだから」は時間的強度、「順序とデータの受渡しがあるから」は連絡的強度、「同じデータを扱うから」は情報的強度になる。

### 1.2 モジュール結合度

モジュール間の依存の強さの尺度である。**強いものから弱い順**に並べる（**弱いほど良い**）。

| 結合度 | 内容 |
| --- | --- |
| 内容結合（最強・最悪） | 他モジュールの内部を直接参照・変更する |
| **共通結合** | **共通域（グローバル領域）に定義したデータを、関係するモジュールが参照する** |
| **外部結合** | **必要なデータを外部宣言して共有する** |
| **制御結合** | **制御パラメタを引数として渡し、モジュールの実行順序（動作）を制御する** |
| スタンプ結合 | データ構造（レコード）全体を引数として渡す |
| **データ結合（最弱・最良）** | **入出力に必要なデータ項目だけを引数として渡す** |

**最も結合度が低い（＝最も良い）のはデータ結合**である。必要最小限のデータだけを引数で渡せば、呼ぶ側と呼ばれる側はそのデータの意味だけを共有すればよい。

逆に**共通結合**が悪いのは、グローバル変数を介してつながると「誰がいつ書き換えたか」が追えなくなるからである。あるモジュールを直したら、同じ変数を使う別のモジュールが壊れる──これが変更に弱い設計の典型である。

**制御結合**が悪い理由は少し分かりにくい。`process(data, flag)` のように「flagが1なら登録、2なら更新」と動作を指定する形にすると、**呼ぶ側が呼ばれる側の内部ロジックを知っていることになる**。呼ばれる側の処理を増やせば呼ぶ側も直す必要が出る。機能ごとに別のモジュールに分ければこの依存は消える。

> **出題** モジュール強度: H29午前I問16 ｜ モジュール結合度: R5午前I問16

## 2. オブジェクト指向設計

### 2.1 クラス間の2つの関係

オブジェクト指向には代表的な関係が2つある。

| 関係 | 意味 | 読み方 |
| --- | --- | --- |
| **is-a 関係** | **汎化・継承**の関係 | 「AはBの一種である」 |
| **part-of 関係** | **集約**の関係 | 「AはBの一部である」 |

判別は**日本語で読み下してみる**のが確実である。

| 組 | 読み下し | 関係 |
| --- | --- | --- |
| タイヤと自動車 | タイヤは自動車の**一部である** | **part-of** |
| 人間と動物 | 人間は動物の**一種である** | **is-a** |
| 辞書と書物 | 辞書は書物の**一種である** | **is-a** |

「辞書と書物」で迷いやすいが、辞書は書物の部品ではなく**書物というカテゴリに属するもの**なので is-a である。

UMLのクラス図では、is-a 関係は**白抜きの三角形の矢印**（汎化）、part-of 関係は**ひし形**（集約・コンポジション）で表す。

### 2.2 汎化と特化

| 用語 | 向き |
| --- | --- |
| **汎化** | **下位クラスの共通部分を抽出して上位クラスとして定義する**（ボトムアップ） |
| 特化 | 上位クラスから、違いを加えて下位クラスを定義する（トップダウン） |

「バス」「トラック」などのクラスの共通部分を抽出して「自動車」クラスとして定義することは**汎化**である。逆に「自動車」から「バス」「トラック」を導くのが特化になる。**上位を作るのが汎化、下位を作るのが特化**と覚える。

関連する用語も区別しておく。**インスタンス**はクラスから生成された実体のことであり、クラス間の関係ではない。「バス」「トラック」は「自動車」のインスタンスでもオブジェクトでもなく、**サブクラス**である。

### 2.3 クラス間の関係の性質

R6で問われた、オブジェクト指向の正しい記述は、

> **サブクラスではスーパークラスの操作を再定義することができる。**

これが**オーバーライド**であり、継承の中心的な機能である。共通の振る舞いはスーパークラスに書き、クラスごとに違う部分だけサブクラスで上書きする。これによって「共通部分を1か所にまとめつつ、個別の違いにも対応する」ことが両立する。

誤答として並ぶ記述を確認する。

| 記述 | 誤りの理由 |
| --- | --- |
| クラス間の関連は、二つのクラス間でだけ定義できる | 3つ以上のクラス間の関連（n項関連）も定義できる |
| サブクラスのインスタンスがスーパークラスの操作を実行するときは、スーパークラスのインスタンスに操作を依頼する | **スーパークラスのインスタンスは存在しない**。継承された操作はサブクラスのインスタンス自身が実行する |
| 集約の関係があるとき、集約オブジェクトは部分オブジェクトと属性及び操作を共有する | 集約は「部品として持つ」関係であり、**属性や操作を共有（継承）するわけではない**。共有するのは is-a（継承）の関係 |

**継承（is-a）では属性・操作が引き継がれるが、集約（part-of）では引き継がれない**という違いが、ここでも効いている。

> **出題** is-a と part-of: H22午前II問24、H27午前II問24 ｜ 汎化: H23午前II問24、H25午前II問25 ｜ クラス間の関係: R6午前I問16

## 3. モデリング言語

### 3.1 状態遷移図

**状態遷移図**は、

> **事象の発生と、そのときの状態に応じたシステムの動作を記述する**

表記法である。**通信プロトコルの記述**に最も適している。

通信プロトコルがこの表記に向くのは、プロトコルが本質的に状態機械だからである。TCPを例にとれば、LISTEN状態でSYNを受け取ればSYN-RECEIVEDへ、ESTABLISHED状態でFINを受け取れば別の状態へ、というように**「いまどの状態か」と「何が起きたか」の組合せで次の動作が決まる**（→ [10-3 通信プロトコル](../10-network/10-3-通信プロトコル.md)）。この構造をそのまま図にできる。

誤答として並ぶ技法との区別も押さえる。**決定表**は条件の組合せを表で表すもの（状態の遷移は表せない）、**データフローダイアグラム**はデータの流れ、**特性要因図**は原因の分析（→ [22-2 業務分析・データ利活用](../22-corporate-activities/22-2-業務分析-データ利活用.md)）であり、いずれも状態遷移は扱わない。

### 3.2 MDA

**MDA（Model Driven Architecture）**は、

> **システムをプラットフォームに依存する部分と依存しない部分とに分けてモデル化する**

技法である。組込みソフトウェアなどの設計に有効とされる。

- **PIM（プラットフォーム非依存モデル）**：業務ロジックそのもの。どのOS・どのハードウェアでも変わらない
- **PSM（プラットフォーム依存モデル）**：特定の環境向けに変換したモデル

分ける理由は、**プラットフォームが変わっても業務ロジックは変わらない**からである。組込み機器では同じ機能を異なるマイコン向けに作り分けることが多く、そのたびに全体を書き直すのは無駄が大きい。業務ロジックをPIMとして一度記述しておけば、プラットフォームごとにPSMへ変換して対応できる。

### 3.3 SysML

**SysML（Systems Modeling Language）**は、

> **システムの設計及び検証を行うために用いられる、UML仕様の一部を流用して機能拡張したグラフィカルなモデリング言語**

である。UMLがソフトウェアを対象にするのに対し、SysMLは**ハードウェアや人間も含めたシステム全体**を対象にする。要求図やパラメトリック図といった、UMLにはない図が追加されている。

誤答として並ぶ言語との区別を押さえる。

| 記述 | 実際は何か |
| --- | --- |
| Webページに画像を使用せずに数式を表示するためのXMLマークアップ言語 | **MathML** |
| ハードウェアとソフトウェアの協調設計（コデザイン）に用いられる、C言語またはC++言語を基にしたシステムレベル記述言語 | **SystemC** |
| 論理合成してFPGAで動作させるハードウェア論理の記述に用いられるハードウェア記述言語 | **VHDL / Verilog HDL** |

> **出題** 状態遷移図: H24午前II問24 ｜ MDA: H24午前II問25 ｜ SysML: R5午前II問24

## 4. アーキテクチャパターン

システム全体の構造について、繰り返し現れる解法をまとめたものが**アーキテクチャパターン**である。『Pattern-Oriented Software Architecture』で整理されたものが出題される。

| パターン | 内容 |
| --- | --- |
| **ブローカー** | **分散環境において、サービスの登録、検索、メッセージのやり取りを行い、クライアントとサーバとの相互依存性を弱める** |
| **マイクロカーネル** | **機能の中核部分と拡張部分とを分離して、変更要求に対する拡張性を向上させる** |
| **パイプフィルタ** | **データストリームに対する一連の処理を、容易に追加又は削除できるように分割して、段階的に実施する** |
| **MVC** | **データの管理、利用者への情報表示、利用者からの入力と制御の三つのコンポーネントでGUIシステムを構成して、表示部分の変更に柔軟に対応する** |
| レイヤ | 機能を階層に分け、上位層は下位層だけに依存させる |

**ブローカー**の本質は**仲介者を置いて直接の依存を断つ**ことにある。クライアントがサーバの所在や実装を直接知っていると、サーバを移動したり差し替えたりするたびにクライアントを直す必要がある。間にブローカーを置き、「このサービスが欲しい」とブローカーに頼む形にすれば、クライアントはサーバの所在を知らなくてよい。[10-5 ネットワーク応用](../10-network/10-5-ネットワーク応用.md) で見たMQTTのパブリッシュ／サブスクライブモデルも、同じ発想のブローカー型である。

どのパターンも、[1. モジュール分割](#1-モジュール分割) で述べた**結合度を下げる**という原則を、システム全体の規模で実現したものだと見ると理解しやすい。

**OSI基本参照モデル**（→ [10-2 データ通信と制御](../10-network/10-2-データ通信と制御.md)）はレイヤパターンの代表例であり、**UNIXのパイプ**はパイプフィルタの代表例である。

> **出題** ブローカーパターン: R7午前II問24

## 5. コード設計

業務システムでは、商品・顧客・部門などにコード（識別子）を割り当てる。コードの付け方にも方式がある。

| 方式 | 内容 |
| --- | --- |
| シーケンスコード（順番コード） | 発生順に連番を振る。単純だが意味を持たない |
| ブロックコード（区分コード） | 1〜99は関東、100〜199は関西、のように区分ごとに範囲を割り当てる |
| 桁別コード | 桁ごとに意味を持たせる |
| デシマルコード（10進コード） | 10進分類で階層的に分類する |
| **ニモニックコード（記憶コード）** | **コードの値からデータの対象物が連想できる**。「TKY」で東京、「BLK」で黒など |

**ニモニックコードは「連想できる」が決め手**である。人が覚えやすく入力ミスにも気づきやすい反面、対象が増えると適切な略号が枯渇し、命名規則が破綻しやすい。

コード設計では、**桁数の見積り**も重要になる。英大文字26種類を使う $n$ 桁のコードで表せる組合せは $26^n$ 通りなので、将来の件数の増加を見込んで桁数を決める（この種の計算は → [1-1 離散数学](../01-basic-theory/1-1-離散数学.md)）。一度運用を始めたコードの桁数変更は影響範囲が広いので、**余裕をもって設計する**のが鉄則である。

> **出題** コード設計: H27午前I問8

## 6. 設計の妥当性を確かめる — レビュー

設計の誤りは、後工程に進むほど修正コストが跳ね上がる。そこで**その工程のうちに、人の目で成果物を検証する**のがレビューである。

**デザインレビューの目的**は、

> **設計工程内で、設計工程の成果物の問題点を発見する。**

重要なのは**「設計工程内で」**という点である。テスト工程まで持ち越さず、**その場で見つけて直す**ことに価値がある。

誤答として並ぶ記述との区別も押さえる。「品質保証部門が全成果物の出荷の可否を判定する」（出荷判定）、「サンプリング検査で品質上の問題点を発見する」（抜取検査）、「プロジェクトマネジメントのプロセス上の問題点を発見する」（プロジェクトレビュー）は、いずれもデザインレビューではない。**レビューするのは設計の成果物であって、プロセスでも出荷判断でもない**。

### 6.1 レビュー技法の種類

| 技法 | 特徴 |
| --- | --- |
| **インスペクション** | **作業成果物の作成者以外の参加者がモデレータとしてレビューを主導し、公式な記録及び分析を行う** |
| ウォークスルー | 作成者が主導し、参加者に説明しながら進める。非公式 |
| パスアラウンド | 成果物を回覧してコメントをもらう |
| ペアプログラミング | 2人1組で、一方が書き他方が随時確認する（→ [13-1 開発プロセス・手法](../13-software-development-management/13-1-開発プロセス-手法.md)） |

**インスペクションとウォークスルーの違いは「誰が主導するか」と「公式か否か」**である。

- **インスペクション**は**作成者以外のモデレータ（進行役）が主導**し、手順も記録も定められた**公式な**レビューである。
- **ウォークスルー**は**作成者が主導**する**非公式な**レビューで、気軽に開ける反面、作成者の思い込みが残りやすい。

インスペクションが作成者を進行役から外すのは、**作成者は自分の成果物の誤りに気づきにくい**という経験則による。第三者が手順に沿って検証することで、見落としを構造的に減らす。その代わり準備と工数がかかるので、重要な成果物に絞って適用する。

> **出題** インスペクション: R1午前I問16 ｜ デザインレビュー: R7午前I問16

## 7. 設計上の判断の例 — タイムアウト

設計では、個々のパラメタをどう決めるかも問われる。Webシステムのタイムアウト設定が出題されている。

Webサーバ、APサーバ、DBサーバの3層構成で、次の3つのタイムアウトを設定するとき、**設定する時間が長い順**はどうなるか。

| 記号 | タイムアウトの種類 |
| --- | --- |
| ① | APサーバのAPが、処理を開始してから終了するまで |
| ② | APサーバのAPにおいて、DBアクセスなどのトランザクションを開始してから終了するまで |
| ③ | Webサーバが、APサーバにリクエストを送信してから返信を受けるまで |

答えは **③ → ① → ②** である。

理由は処理の**入れ子構造**にある。

```
③ Webサーバ → APサーバへのリクエスト
  └─ ① APの処理全体
       └─ ② DBトランザクション
```

②は①の中で行われ、①は③の中で行われる。**外側の処理時間は内側の処理時間を必ず含む**ので、タイムアウト値も外側ほど長くなければ辻褄が合わない。

もし内側のタイムアウトを外側より長く設定するとどうなるか。DBの応答が遅れたとき、内側（②）がまだ待っているのに外側（③）が先に諦めてしまう。Webサーバは「失敗」と判断してエラーを返すが、APサーバとDBサーバは処理を続けている。**利用者にはエラーが見えているのに裏では処理が走っている**という、最も厄介な不整合が生じる。

「外側ほど長く」という原則は、タイムアウトに限らず**リトライ回数や有効期限の設計**でも同じように成り立つ。

> **出題** タイムアウト設計: H28午前II問23

## この章のまとめ

- 良い設計とは**変更に強い設計**。そのための2つのものさしが**モジュール強度（高いほど良い）とモジュール結合度（低いほど良い）**である。
- 強度は**なぜまとめたかの理由**で判別する。**データとともにまとめて外から隠したのが情報的強度**。結合度は**引数で必要なデータだけを渡すデータ結合が最良**、**共通域の共有が最悪に近い**。
- **is-a は継承（一種である）、part-of は集約（一部である）**。**共通部分を抽出して上位クラスを作るのが汎化**。継承では属性・操作が引き継がれるが、集約では引き継がれない。
- **状態遷移図は通信プロトコルの記述に適する**。**MDAはプラットフォーム依存／非依存を分けてモデル化**。**SysMLはUMLを拡張してシステム全体を扱う**。
- アーキテクチャパターンは**ブローカー＝仲介して依存を弱める、マイクロカーネル＝中核と拡張の分離、パイプフィルタ＝段階的処理、MVC＝表示と制御とデータの分離**。
- **ニモニックコードはコードから対象物が連想できる**。
- **インスペクションは作成者以外のモデレータが主導する公式なレビュー**、ウォークスルーは作成者主導で非公式。
- タイムアウトは**処理の入れ子に合わせて外側ほど長く**設定する。
