# 12-6 保守・廃棄

稼働を始めたソフトウェアを**直し続け、やがて終わらせる**工程を扱う。

ソフトウェアの一生で、開発に要する期間より保守に要する期間のほうがはるかに長い。コストで見ても保守が大半を占める。にもかかわらず保守が軽く見られがちなのは、「完成したものを直すだけ」という誤解があるからである。実際には、**作った人がいなくなり、設計書は古く、なぜそう書かれているかわからないコードを、業務を止めずに直す**という難しい仕事になる。本章の技法（リバースエンジニアリング、リファクタリング）は、この困難に対処するためのものである。

ネットワークスペシャリスト午前IIでは問25前後から、午前Iでは問17前後から出題される。16年で4問。

## 1. ソフトウェア保守の分類

**JIS X 0161（ISO/IEC 14764）**では、保守を4つに分類している。**「問題が起きているか」と「何のために直すか」**の2軸で整理できる。

| 分類 | 内容 | 契機 |
| --- | --- | --- |
| **是正保守** | 発見された**問題を訂正する** | 障害が発生した |
| **予防保守** | **潜在的な障害が顕在化する前に**発見して訂正する | **問題は起きていない** |
| **適応保守** | 環境の変化（OS更新、法改正、組織変更など）に**適応させる** | 外部環境が変わった |
| **完全化保守** | **性能や保守性を改善する** | より良くしたい |

区別の鍵は**「問題が発生しているかどうか」**である。

> 問題は発生していないが、プログラムの仕様書と現状のソースコードとの不整合を解消するために、リバースエンジニアリングの手法を使って仕様書を作成し直す。これはソフトウェア保守のどの分類に該当するか。

答えは**予防保守**である。「問題は発生していないが」という書き出しが決め手になる。仕様書とコードが食い違ったまま放置すれば、将来の改修で**仕様書を信じた誤った修正**が入り、障害につながる。それを未然に防ぐ行為なので予防保守に当たる。

是正保守（問題が起きてから直す）でも、適応保守（環境が変わったから直す）でも、完全化保守（性能を上げたい）でもない点を確認しておく。

## 2. リバースエンジニアリングと関連技術

**リバースエンジニアリング**とは、

> **既存のソフトウェアを解析し、その仕様や構造を明らかにする。**

> **ソースプログラムを解析してプログラム仕様書を作る。**

通常の開発が「仕様書 → ソースコード」と進むのに対し、**逆方向に遡る**のでリバース（逆）と呼ばれる。

なぜ必要になるか。長年保守されたシステムでは、**設計書が現状と合っていない**ことが珍しくない。改修のたびにコードだけ直して文書を更新しなかった結果、残された設計書は信用できず、唯一の正確な情報源がソースコードだけになる。この状態で改修しようとすれば、まずコードから現状を把握するしかない。

関連する用語との区別が繰り返し問われる。**向き**で整理すると覚えやすい。

| 用語 | 向き・内容 |
| --- | --- |
| **フォワードエンジニアリング** | **設計情報からソースコードを自動生成する**（通常の向き） |
| **リバースエンジニアリング** | **既存のソフトウェアを解析し、仕様や構造を明らかにする**（逆向き） |
| **リエンジニアリング** | **既存のソフトウェアを分析し理解した上で、ソフトウェア全体を新しく構築し直す**（逆向き＋順向き） |
| **リファクタリング** | **外部から見た振る舞いを変えずに、内部構造を変える** |

**リエンジニアリングはリバースとフォワードの組合せ**である。まず既存システムを解析して仕様を取り出し（リバース）、それをもとに新しい技術で作り直す（フォワード）。老朽化したシステムの刷新（マイグレーション）で行われる。

誤答として並ぶ他の記述も確認する。

- 「**ソースプログラムを探索して修正箇所や影響度を調べる**」→ 影響分析（インパクト分析）
- 「**ソースプログラムを見直して構造化されたプログラムに変換する**」→ 構造化（リストラクチャリング）
- 「**ソースプログラムを分かりやすい表現に書き換える**」→ リファクタリングに近い
- 「ソフトウェア部品を組み合わせてシステムを開発する」→ コンポーネントベース開発
- 「プログラムの修正が他の部分に影響していないかどうかをテストする」→ **回帰テスト（リグレッションテスト）**

なお、他社製品の**リバースエンジニアリング**は、著作権や契約との関係が問題になる場合がある（→ [13-2 知的財産適用管理](../13-software-development-management/13-2-知的財産適用管理.md)）。また、公開されたプロトコル仕様に基づいて同等機能のソフトウェアを独自に開発することは著作権侵害に当たらない一方、ソースコードを複製すれば侵害になる、という線引きがある。

> **出題** リバースエンジニアリング: H26午前II問25、R3午前II問25 ｜ ソフトウェア保守の分類: R4午前I問17

## 3. リファクタリング

**リファクタリング**とは、

> **外部から見た振る舞いを変更せずに、保守性が高いプログラムに書き直す。**

**「外から見た動きは一切変えない」**ことが定義に含まれている点が重要である。機能追加もバグ修正も伴わない。重複したコードをまとめる、長すぎる関数を分割する、分かりにくい変数名を改める──こうした**内部構造だけの改善**を指す。

一見すると何も生み出していないように見えるが、保守の文脈では明確な価値がある。[12-2 設計](12-2-設計.md) で述べたとおり、変更に強いかどうかは構造で決まる。構造が崩れたまま機能追加を重ねれば、改修のたびにコストが増え、やがて手がつけられなくなる。**リファクタリングは将来の改修コストを下げるための投資**であり、分類としては**完全化保守**に当たる。

リファクタリングを安全に行うには、**回帰テストが自動化されていること**が前提になる。振る舞いを変えていないことを確認する手段がなければ、改善のつもりが改悪になる。アジャイル開発でテスト自動化とリファクタリングがセットで語られるのはこのためである（→ [13-1 開発プロセス・手法](../13-software-development-management/13-1-開発プロセス-手法.md)）。

誤答との区別も押さえる。「ソースコードから設計書を再作成する」はリバースエンジニアリング、「ソフトウェア部品を組み合わせて開発する」はコンポーネントベース開発、「修正が他の部分に影響していないかをテストする」は回帰テストである。

> **出題** リファクタリング: H30午前II問25

## 4. 廃棄

システムには終わりがある。**廃棄（除却）**の工程で考えるべきことを挙げる。

| 観点 | 内容 |
| --- | --- |
| データの移行・保管 | 後継システムへ移すデータと、法定保存期間のため保管するデータを切り分ける |
| **データの確実な消去** | 記憶媒体を廃棄・再利用する前に、復元できない形で消去する |
| ライセンスの整理 | 使用許諾契約の終了手続きを行う |
| 関係者への周知 | 利用者・取引先へ停止日を通知する |

**データの消去**はセキュリティ上の重要事項である。ファイルを削除しただけ、フォーマットしただけでは**データは復元できる**。物理的破壊、専用ソフトウェアによる上書き消去、暗号化消去（鍵の破棄）といった方法で、確実に読み出せない状態にする必要がある。中古機器や廃棄ディスクから情報が流出する事故は繰り返し起きており、廃棄は開発の付け足しではなく、情報セキュリティ管理の一部として扱うべき工程である（→ [11-2 情報セキュリティ管理](../11-security/11-2-情報セキュリティ管理.md)）。

## この章のまとめ

- 保守の4分類は**是正（問題を訂正）、予防（問題が起きる前に手を打つ）、適応（環境変化に合わせる）、完全化（性能・保守性を改善）**。**「問題は発生していないが」とあれば予防保守**。
- **リバースエンジニアリングはソースコードから仕様・構造を明らかにする**。**フォワードは設計からコードを生成、リエンジニアリングは両者を合わせて作り直す**。
- **リファクタリングは外部から見た振る舞いを変えずに内部構造を改善する**。回帰テストの自動化が前提になる。
- 廃棄工程では**データの確実な消去**が重要。削除やフォーマットでは復元できてしまう。
