# 13-4 構成管理・変更管理

開発の過程で生まれる**成果物を識別し、変更を統制する**仕組みを扱う。

複数人が同じソースコードを同時に直し、仕様は途中で変わり、本番には複数のバージョンが並行して存在する。この状況で「いま本番で動いているのはどのコードか」「この修正はどの版に入っているか」が分からなくなれば、障害対応も改修も成り立たない。構成管理はこの混乱を防ぐための土台である。

午前Iの問18前後から出題されるが、16年で1問と出題は少ない。

出題が少ない分野のため、本章では過去問で問われた内容に加えて、構成管理と変更管理の実務的な整理を補っている。

## 1. 構成管理とは

**構成管理（コンフィギュレーションマネジメント）**は、開発の成果物を**構成品目**として識別し、その状態と変更履歴を管理する活動である。

目的は次の問いに常に答えられるようにすることである。

- いま本番で動いているのは、どのバージョンの何の組合せか
- ある修正は、どのバージョンから入っているか
- 過去の任意の時点の状態を、正確に再現できるか

3つ目が特に重要である。本番で障害が起きたとき、**そのとき動いていたコードを正確に取り出せなければ原因の調査ができない**。構成管理は、いわば「いつでも過去に戻れる」状態を保つ仕組みである。

---

## 2. 構成管理の対象

**ソフトウェア開発プロジェクトで行う構成管理の対象項目**として適切なのは、

> **プログラムのバージョン**

である。構成管理が扱うのは、**システムを構成する「もの」とその版**である。

誤答として並ぶ項目との区別を押さえる。

| 項目 | 何の管理か |
| --- | --- |
| **プログラムのバージョン** | **構成管理** |
| 開発作業の進捗状況 | 進捗管理（→ [14-6 プロジェクトの時間](../14-project-management/14-6-プロジェクトの時間.md)） |
| 成果物に対するレビューの実施結果 | 品質管理（→ [14-9 プロジェクトの品質](../14-project-management/14-9-プロジェクトの品質.md)） |
| プロジェクト組織の編成 | 資源管理（→ [14-5 プロジェクトの資源](../14-project-management/14-5-プロジェクトの資源.md)） |

判別の基準は**「成果物そのものか、それ以外か」**である。進捗・レビュー結果・組織編成は、いずれもプロジェクトの**状態や活動**に関する情報であって、システムを構成する品目ではない。

構成品目になるのは次のようなものである。

- ソースコード、実行モジュール
- 設計書、仕様書、マニュアル
- テスト仕様書、テストデータ
- 設定ファイル、構築手順（→ [13-3 開発環境管理](13-3-開発環境管理.md) のIaCコード）
- 使用しているライブラリとそのバージョン

> **出題** 構成管理の対象項目: H26午前I問18

## 3. バージョン管理

構成管理を実際に支えるのが**バージョン管理システム**である。

| 用語 | 内容 |
| --- | --- |
| リポジトリ | 成果物と全履歴を保管する場所 |
| コミット | 変更を履歴として記録する |
| **ブランチ** | 履歴を枝分かれさせ、並行して作業する |
| **マージ** | 枝分かれした変更を統合する |
| **タグ** | 特定の時点に名前を付ける（リリース版の目印） |
| **ベースライン** | **正式に承認され、以降の変更は変更管理手続きを経なければならない基準点** |

**ベースライン**の考え方が構成管理の要である。ある時点の成果物を「これが基準だ」と確定させると、それ以降の変更は**勝手にはできず、承認を経る必要がある**。これによって「誰かが黙って直していた」という事態を防ぎ、変更の履歴を追跡可能にする。

ブランチとマージは、複数人・複数バージョンの並行開発を可能にする。本番用の修正（ホットフィックス）と次期版の開発を同時に進め、後で統合する、といった運用ができる。

## 4. 変更管理

**変更管理**は、**変更の要求を受け付け、影響を評価し、承認・却下を決め、実施して記録する**一連の手続きである。

```mermaid
graph LR
  A["変更要求の受付"] --> B["影響分析<br/>（範囲・工数・リスク）"]
  B --> C["承認／却下の判断"]
  C --> D["実施"]
  D --> E["検証と記録"]
```

### 4.1 なぜ手続きが要るか

変更そのものは避けられない。問題は**無制御な変更**である。要求されるままに次々と変更を入れれば、

- 予定した期間と費用を超過する（**スコープクリープ**）
- 変更が別の箇所を壊す
- 何が変わったのか誰も把握できなくなる

という事態になる。変更管理は変更を**禁じる**のではなく、**影響を見積もったうえで、決める権限のある者が決める**ようにするものである。

### 4.2 影響分析

変更を承認する前に、**どこまで波及するかを見積もる**必要がある。ソースコードを探索して修正箇所と影響範囲を調べる作業がこれに当たる（→ [12-6 保守・廃棄](../12-system-development/12-6-保守-廃棄.md)）。構成管理が機能していれば、「この部品を使っているのはどのモジュールか」を追跡でき、影響分析の精度が上がる。

変更後には、**修正が他の部分に影響していないかを確かめる回帰テスト（リグレッションテスト）**を行う（→ [12-4 統合・テスト](../12-system-development/12-4-統合-テスト.md)）。

### 4.3 開発における変更管理とITサービスにおける変更管理

同じ「変更管理」という語が、開発工程とITサービス運用の両方で使われる。

| 文脈 | 対象 | 参照 |
| --- | --- | --- |
| ソフトウェア開発 | 設計・コード・仕様の変更 | 本章 |
| プロジェクトマネジメント | プロジェクトの計画・スコープの変更 | [14-2 プロジェクトの統合](../14-project-management/14-2-プロジェクトの統合.md) |
| ITサービスマネジメント | 稼働中のサービス・構成品目の変更 | [15-2 サービスマネジメントシステムの計画及び運用](../15-service-management/15-2-サービスマネジメントシステムの計画及び運用.md) |

対象は違うが、**「要求 → 影響評価 → 承認 → 実施 → 記録」という骨格は共通**している。設問で問われているのがどの文脈かを読み分ければ、答えは同じ構造から導ける。

## この章のまとめ

- **構成管理の対象は「システムを構成する成果物とその版」**。**プログラムのバージョン**は対象だが、進捗状況・レビュー結果・組織編成は別の管理領域である。
- **ベースラインは、以降の変更に承認手続きを要する基準点**。これが変更の追跡可能性を支える。
- **変更管理は変更を禁じるのではなく、影響を評価したうえで権限のある者が決める**仕組み。無制御な変更はスコープクリープと品質低下を招く。
- 開発・プロジェクト・ITサービスで対象は異なるが、**「要求→影響評価→承認→実施→記録」という骨格は共通**している。
