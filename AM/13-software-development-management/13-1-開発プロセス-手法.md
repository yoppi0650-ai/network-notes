# 13-1 開発プロセス・手法

ソフトウェアを**どういう手順と体制で作るか**という、開発の進め方そのものを扱う。

[12章](../12-system-development/12-1-システム-ソフトウェア-要件定義.md) が「各工程で何をするか」だったのに対し、ここでは「工程をどう並べ、どう回すか」を考える。ウォータフォールとアジャイルの対立も、CMMIによる成熟度評価も、根底にあるのは**不確実性にどう向き合うか**という問いである。要件が最初から確定できるなら順に進めればよいが、やってみないとわからないなら作りながら決めるしかない。どちらが正しいかではなく、**どういう状況でどちらが有効か**を押さえるのがこの分野の勘所である。

ネットワークスペシャリスト午前IIでは問25前後から、午前Iでは問17前後から出題される。16年で8問。近年は**アジャイル・スクラム**の出題が増えている。

## 1. 開発モデル

| モデル | 進め方 | 向く状況 |
| --- | --- | --- |
| ウォータフォールモデル | 工程を順に進め、前工程に戻らないことを原則とする | 要件が安定し、規模が大きく、品質保証の証跡が要る場合 |
| プロトタイピングモデル | 試作品を作って利用者に確認しながら進める | 要件が曖昧で、利用者と認識を合わせる必要がある場合 |
| スパイラルモデル | 部分ごとに「設計→実装→評価」を繰り返して育てる | リスクの高い部分を先に潰したい場合 |
| **アジャイル開発** | 短い反復で動くソフトウェアを作り続ける | **要件の変化が前提の場合** |

ウォータフォールが批判される理由は、**要件が最後まで変わらないという前提が現実と合わないこと**にある。設計が終わってから半年後に動くものが出てきたとき、利用者が「思っていたのと違う」と言うのは珍しくない。しかしそのときには手戻りのコストが膨大になっている。

逆にウォータフォールが選ばれ続ける理由もある。**工程ごとの成果物と承認が残る**ので、発注者と受注者の責任範囲を契約で切り分けやすい。大規模で関係者が多いほど、この性質は重要になる（→ [18-3 調達計画及び実施](../18-system-planning/18-3-調達計画及び実施.md)）。

## 2. 共通フレーム

**共通フレーム（SLCP-JCF）**は、

> **取得者（発注者）と供給者（受注者）の二者間取引を明確化するためのものであり、業務分析、業務設計、ソフトウェアを中心としたシステムの企画、要件定義、開発、運用、保守及びそれらにかかわる諸活動を対象としており、国際規格（ISO/IEC 12207）に適合している。**

要点は**「二者間取引を明確化する」**ことにある。発注者と受注者が「要件定義」「設計」という言葉を別の意味で使っていては、どこまでが誰の責任かが曖昧になる。共通フレームは**作業内容と用語の共通の物差し**を与える。

### 2.1 テーラリング

共通フレームの適用で最も問われるのが、**そのまま使うものではない**という点である。

> **プロジェクトの特性や開発モデルに合わせて、アクティビティやタスクを取捨選択して適用する。**

これを**テーラリング（修整）**という。共通フレームはあらゆるプロジェクトで必要になりうる作業を網羅した「カタログ」であって、全項目を実施することを求めてはいない。小規模なプロジェクトで全部やれば、作業そのものより文書作成のほうが重くなってしまう。

誤答として並ぶ記述を確認する。

| 記述 | 誤りの理由 |
| --- | --- |
| JIS規格に基づいているので、個々のプロジェクトの都合でアクティビティやタスクを変えずにそのまま適用する | **テーラリングが前提**である |
| 共通フレームで規定しているプロセスの実施順序に合わせて作業手順を決める | **共通フレームは実施順序を規定していない**。何をするかを示すだけで、どの順でやるかは開発モデルが決める |
| 共通フレームで推奨している開発モデル、技法やツールを取捨選択して適用する | **共通フレームは特定の開発モデル・技法・ツールを推奨していない** |

共通フレームが順序もモデルも規定しないのは、**ウォータフォールでもアジャイルでも使えるようにするため**である。「何をすべきか」と「どう進めるか」を分離しておけば、進め方が変わっても共通の用語で話せる。

> **出題** 共通フレーム: H21午前I問17 ｜ 共通フレームの適用: H27午前I問17

## 3. アジャイル開発

**アジャイル開発**は、短い期間（**イテレーション**、スクラムでは**スプリント**）で「計画→設計→実装→テスト」を一巡させ、**動くソフトウェアを繰り返し作る**方法である。

**イテレーションを行う目的**は、

> **ソフトウェアに存在する顧客の要求との不一致を短いサイクルで解消したり、要求の変化に柔軟に対応したりする。**

鍵は**「不一致を早く見つける」**ことにある。仕様書の上で合意しても、実際に動くものを見ると認識の違いが露呈する。これは避けられないので、**露呈するまでの時間を短くする**という発想に切り替える。1〜4週間ごとに動くものを見せれば、ずれは最大でも1イテレーション分で済む。

誤答として並ぶのは、いずれもアジャイルの**別のプラクティス**の目的である。

| 記述 | 実際は何の目的か |
| --- | --- |
| タスクの実施状況を可視化して、いつでも確認できるようにする | タスクボード（かんばん） |
| ペアプログラミングのドライバとナビゲータを固定化させない | ペアプログラミングの運用 |
| 毎日決めた時刻にチームメンバが集まって開発の状況を共有する | **デイリースクラム（朝会）** |

**イテレーションの目的は「要求とのずれの解消」**であって、進捗の可視化や情報共有ではない。

## 4. スクラム

**スクラム**はアジャイル開発の代表的なフレームワークである。役割・イベント・成果物が明確に定義されている。

### 4.1 3つの役割

| 役割 | 責任 |
| --- | --- |
| **プロダクトオーナ** | **ゴールとミッションが達成できるように、プロダクトバックログのアイテムの優先順位を決定する** |
| **スクラムマスタ** | **チームのコーチやファシリテータとして、スクラムが円滑に進むように支援する** |
| **開発チーム** | **プロダクトを完成させるための具体的な作り方を決定し、リリース判断可能なインクリメントを完成させる** |

**プロダクトオーナは「何を、どの順で作るか」を決め、開発チームは「どう作るか」を決める**。この分離が重要である。プロダクトオーナが作り方まで指示すれば開発チームの自律性が失われ、開発チームが優先順位を決めれば事業上の価値と乖離する。

**スクラムマスタは管理者ではない**。進捗を管理したり指示を出したりするのではなく、**チームが自律的に動けるよう障害を取り除く**のが役割である。「支援する」「ファシリテータ」という表現が手がかりになる。

### 4.2 主なイベント

| イベント | 内容 |
| --- | --- |
| スプリントプランニング | スプリントで何をどう作るかを計画する |
| デイリースクラム | 毎日短時間、進捗と障害を共有する |
| **スプリントレビュー** | **ステークホルダに作業の結果をプレゼンテーションして、プロダクトゴールに対する進捗について話し合い、必要に応じてスコープを調整する** |
| レトロスペクティブ（振り返り） | **チームの仕事の進め方**を振り返り、改善する |

**スプリントレビューとレトロスペクティブの違い**がよく問われる。

- **スプリントレビューは「作ったもの（プロダクト）」をステークホルダに見せて評価する**。外向きの会である。
- **レトロスペクティブは「作り方（プロセス）」をチーム内で振り返る**。内向きの会である。

「ステークホルダに」「プロダクトゴールに対する進捗」「スコープを調整」というキーワードが出てきたらスプリントレビューである。

> **出題** アジャイルのイテレーション: H30午前I問17 ｜ プロダクトオーナ: R3午前I問17 ｜ スプリントレビュー: R7午前I問17

## 5. XP

**XP（eXtreme Programming）**はアジャイル開発の手法の一つで、具体的な実践（プラクティス）が定められている。

| プラクティス | 内容 |
| --- | --- |
| **ペアプログラミング** | **2人1組でプログラミングを行う**。1人がコードを書き（ドライバ）、もう1人が確認・助言する（ナビゲータ） |
| テスト駆動開発（TDD） | テストを先に書いてから実装する |
| リファクタリング | 振る舞いを変えずに内部構造を改善する（→ [12-6 保守・廃棄](../12-system-development/12-6-保守-廃棄.md)） |
| 継続的インテグレーション | 頻繁に統合してビルド・テストする |
| 小さなリリース | 短い間隔でリリースする |
| 計画ゲーム | 顧客と開発者が協力して計画を立てる |

**XPのプラクティスとして出題されるのはペアプログラミング**である。誤答に並ぶ「構造化プログラミング」「コンポーネント指向プログラミング」「ビジュアルプログラミング」は、いずれもプログラミングの**方式**であってXPのプラクティスではない。

ペアプログラミングは一見すると人員を2倍使う非効率な方法に見えるが、**レビューを常時行っているのと同じ効果**がある（→ [12-2 設計](../12-system-development/12-2-設計.md)）。誤りをその場で防ぎ、知識が自然に共有され、属人化も防げる。書く速度は落ちても、手戻りを含めた全体では引き合うという考え方である。

> **出題** XPのプラクティス: H29午前II問25

## 6. CMMI

**CMMI（Capability Maturity Model Integration、能力成熟度モデル統合）**は、

> **ソフトウェア開発組織及びプロジェクトのプロセスの成熟度を評価するためのモデル**

である。評価するのは**成果物の品質ではなくプロセスの成熟度**である点が核心になる。「今回はうまくいった」ではなく「いつもうまくいく仕組みがあるか」を見る。

### 6.1 成熟度レベル

| レベル | 状態 |
| --- | --- |
| 1 初期 | 場当たり的。成功は個人の力量に依存する |
| **2 管理された** | **作業成果物の状況が、主要なタスクの完了時点で管理層に対して見える状態になっている**。プロジェクト単位で管理されている |
| **3 定義された** | **プロセスが明文化されて、組織内の全ての人がそれを利用している**。組織標準がある |
| **4 定量的に管理された** | **実績が定量的に把握されており、プロセスが組織的に管理されている** |
| **5 最適化している** | **プロセスを継続的に改善していくための仕組みが機能している**（最高レベル） |

**最も高いレベル5は「継続的に改善する仕組みが機能している」**ことである。

レベルの並びには一貫した論理がある。まず**見えるようにし**（2）、次に**組織で共有し**（3）、次に**数値で測り**（4）、最後に**測った数値をもとに改善を回す**（5）。測定できないものは改善できないので、4の定量化なしに5には到達しない、という順序になっている。

誤答との区別も押さえる。CMMIは「ソフトウェア開発のプロセスモデル」（開発モデルそのもの）でも、「システム開発及び取引のための共通フレーム」（これは共通フレーム）でも、「プロジェクトの成熟度に応じて開発手順を定義したモデル」（評価するのは組織・プロセスの成熟度であり、手順を定義するものではない）でもない。

> **出題** CMMI: H29午前I問17 ｜ CMMIの成熟度レベル: H23午前II問25

## この章のまとめ

- 開発モデルの選択は**要件の不確実性への向き合い方**で決まる。要件が安定ならウォータフォール、変化が前提ならアジャイル。
- **共通フレームは二者間取引を明確化する共通の物差し**。**テーラリング（取捨選択）が前提**で、実施順序も特定の技法も規定しない。
- **イテレーションの目的は顧客の要求との不一致を短いサイクルで解消すること**。
- スクラムの役割は**プロダクトオーナ＝優先順位、開発チーム＝作り方、スクラムマスタ＝支援**。**スプリントレビューはプロダクトを外部に見せる会、レトロスペクティブはプロセスを内部で振り返る会**。
- **XPのプラクティスの代表はペアプログラミング**。
- **CMMIはプロセスの成熟度を評価するモデル**。最高の**レベル5は「継続的改善の仕組みが機能している」**状態。
