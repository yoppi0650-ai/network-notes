# 13-3 開発環境管理

開発・テスト・本番という**複数の環境をどう用意し、どう管理するか**を扱う。

開発者の手元では動いたのに本番では動かない──この古典的な問題の原因は、環境の差異にある。OSのバージョン、ミドルウェアの設定、データの量と内容。これらが違えば挙動も変わる。だから環境管理の課題は、突き詰めると**「環境の差異をどう小さくし、どう再現可能にするか」**に尽きる。本章で扱うステージング環境もプロビジョニングツールも、この問いへの答えである。

ネットワークスペシャリスト午前IIでは問25前後から、午前Iでは問17前後から出題される。16年で3問。

## 1. 環境の分離

システム開発では、用途の異なる複数の環境を用意する。

| 環境 | 用途 |
| --- | --- |
| 開発環境 | 開発者が個々にコードを書き、動作を確かめる |
| 結合テスト環境 | モジュールを統合してテストする |
| **ステージング環境** | **本番環境とほぼ同じ構成で、リリース前の最終テストを行う** |
| 本番環境 | 実際に業務で使用する |

環境を分ける目的は明快である。**開発中の不安定なコードを本番に近づけない**ことと、**本番のデータを開発者が自由に触れないようにする**ことである。後者はセキュリティ上も重要で、開発環境で本番の個人情報を使うことは原則として避けるべきである（マスキングや擬似データで代替する）。

## 2. ステージング環境

**ステージング環境**とは、

> **本番環境とほぼ同じ環境を用意して、システムリリース前の最終テストを行う環境**

である。

**「本番環境とほぼ同じ」**であることが本質である。開発環境やテスト環境は、コストや利便性のために本番とは構成が異なるのが普通である。サーバの台数が少ない、ロードバランサがない、データ量が桁違いに少ない、といった違いがある。こうした差異に起因する問題は、**本番と同じ構成でしか再現しない**。

ステージング環境で確認するのは、機能が正しいかどうかよりも、

- 本番と同じ構成・設定で正しく動作するか
- 本番相当のデータ量で性能が足りるか
- リリース手順そのものが正しいか（手順のリハーサル）
- 問題があったときに切り戻せるか

といった点である。つまり**「リリースという作業自体のテスト」**を兼ねている。

誤答として並ぶ記述を確認する。

| 記述 | 実際は何か |
| --- | --- |
| 開発者がプログラムを変更するたびに、サーバに直接デプロイして動作を確認し、デバッグするための環境 | 開発環境 |
| システムのベータ版を広く一般の利用者に公開してテストを実施してもらい、問題点やバグを報告してもらう環境 | **ベータテスト**（公開テスト） |
| 保護するネットワークと外部ネットワークの間に境界ネットワーク（DMZ）を設置してセキュリティを高めたネットワーク環境 | **DMZ**（→ [11-4 情報セキュリティ対策](../11-security/11-4-情報セキュリティ対策.md)） |

**「本番とほぼ同じ」「リリース前の最終テスト」**という2つのキーワードで判別できる。

> **出題** ステージング環境: R4午前II問25、R7午前II問25

## 3. サーバプロビジョニングツール

**サーバプロビジョニングツール**を使用する目的は、

> **システム構成をあらかじめ記述しておくことによって、サーバを自動的に構成する。**

これが **Infrastructure as Code（IaC）**の考え方である。「OSをインストールし、ミドルウェアを入れ、設定ファイルを編集し……」という手順を人が実行するのではなく、**あるべき構成をコードとして記述しておき、ツールに実行させる**。

この方式が解決する問題は3つある。

- **再現性**：同じコードを実行すれば、何台でも同じ構成のサーバができる。「手順書どおりにやったつもりだが1台だけ設定が違う」という事態がなくなる。
- **環境差異の解消**：開発環境・ステージング環境・本番環境を同じコードから構築すれば、[1. 環境の分離](#1-環境の分離) で述べた差異そのものが生まれない。
- **変更履歴の管理**：構成がコードなので、バージョン管理システムで履歴を追える（→ [13-4 構成管理・変更管理](13-4-構成管理-変更管理.md)）。「いつ誰が何を変えたか」が残る。

誤答として並ぶツールとの区別も押さえる。

| 記述 | 実際は何か |
| --- | --- |
| サーバ上のサービスが動作しているかどうかを、他のシステムからリモートで監視する | 死活監視ツール（→ [10-4 ネットワーク管理](../10-network/10-4-ネットワーク管理.md)） |
| サーバにインストールされているソフトウェアを一元的に管理する | 資産管理ツール（ソフトウェア資産管理） |
| サーバを監視して、システムやアプリケーションのパフォーマンスを管理する | 性能監視ツール（APM） |

**「構成を記述して自動構成する」のがプロビジョニング**、「状態を見る」のが監視ツール、という役割の違いで判別できる。

> **出題** サーバプロビジョニングツール: R5午前I問17

## 4. 開発環境の構成要素

開発環境を整えるには、ツールと管理の両面が要る。

| 要素 | 内容 |
| --- | --- |
| 統合開発環境（IDE） | エディタ、コンパイラ、デバッガを統合した開発ツール（→ [5-4 開発ツール](../05-software/5-4-開発ツール.md)） |
| バージョン管理システム | ソースコードの変更履歴を管理する（→ [13-4](13-4-構成管理-変更管理.md)） |
| ビルドツール | コンパイル・リンク・パッケージングを自動化する |
| CI/CDツール | 変更のたびに自動でビルド・テスト・デプロイを行う |
| コンテナ | 実行環境ごとパッケージ化し、どこでも同じ挙動を再現する |

**開発環境の管理では、ライセンスの管理も重要**である。商用の開発ツールやライブラリには利用条件があり、開発用には無償でも本番利用には有償というものもある。OSSを組み込む場合は、そのライセンス条件が自社製品の配布条件に影響する（→ [13-2 知的財産適用管理](13-2-知的財産適用管理.md)、[5-5 オープンソースソフトウェア](../05-software/5-5-オープンソースソフトウェア.md)）。どのバージョンのどのライブラリを使っているかを把握しておくことは、脆弱性対応の面でも必須になる（→ [11-4 情報セキュリティ対策](../11-security/11-4-情報セキュリティ対策.md) のSBOM）。

## この章のまとめ

- 環境管理の課題は**環境間の差異をどう小さくし、どう再現可能にするか**。
- **ステージング環境は「本番環境とほぼ同じ構成」で「リリース前の最終テスト」を行う環境**。リリース手順そのもののリハーサルも兼ねる。
- **サーバプロビジョニングツールは、構成をコードで記述してサーバを自動構成する**（Infrastructure as Code）。再現性・環境差異の解消・変更履歴の管理が得られる。監視ツールや資産管理ツールとは役割が違う。
