# 5-4 開発ツール

ソフトウェア開発を支援する**道具**を扱う。

開発ツールの存在意義は一貫している。**人がやると時間がかかり、しかも間違える作業を機械に任せる**ことである。コンパイル、テストの実行、バグの記録、バージョンの管理──これらを人手で回していては、規模が大きくなるほど破綻する。どのツールが「何を自動化しているか」を押さえると、個々の名前も覚えやすくなる。

午前IIの問25前後から出題される。16年で1問と出題は少ない。

出題が少ない分野のため、本章では過去問で問われた内容に加えて、ツールの分類の整理を補っている。

## 1. ツールの分類

開発の工程に沿って、使われるツールが変わる。

| 工程 | 主なツール |
| --- | --- |
| 設計 | CASEツール、モデリングツール（UML、SysML → [12-2 設計](../12-system-development/12-2-設計.md)） |
| 実装 | エディタ、**コンパイラ**、**インタプリタ**、統合開発環境（IDE）（→ [2-3 プログラム言語](../02-algorithms-and-programming/2-3-プログラム言語.md)） |
| デバッグ | **デバッガ**、トレーサ、静的解析ツール（→ [12-3 実装・構築](../12-system-development/12-3-実装-構築.md)） |
| テスト | **テストツール**、カバレッジ測定ツール（→ [12-4 統合・テスト](../12-system-development/12-4-統合-テスト.md)） |
| 品質管理 | **メトリクス測定ツール** |
| 不具合管理 | **バグトラッキングシステム** |
| 構成管理 | バージョン管理システム（→ [13-4 構成管理・変更管理](../13-software-development-management/13-4-構成管理-変更管理.md)） |
| 環境構築 | ビルドツール、CI/CDツール、プロビジョニングツール（→ [13-3 開発環境管理](../13-software-development-management/13-3-開発環境管理.md)） |

## 2. バグトラッキングシステム

> **バグトラッキングシステム**は、**発見されたバグの内容、バグが発生したソフトウェアのバージョンなどを記録し、その修正計画や修正履歴を管理する**。

**「記録して管理する」**のがこのツールの役割である。バグを見つける道具でも、直す道具でもない。

なぜ専用のツールが必要になるのか。バグは発見から修正完了までに時間差があり、その間に次のバグが見つかる。誰が担当し、どのバージョンで直り、再発していないかを表計算ソフトで追うのは、件数が増えれば必ず破綻する。**状態（未着手・対応中・修正済・確認済・クローズ）をもつ項目を多数並行して管理する**という性質が、専用ツールを必要とさせている。

[13-4 構成管理・変更管理](../13-software-development-management/13-4-構成管理-変更管理.md) で見た変更管理の手続きを、不具合に特化して支援する道具だと位置づけるとよい。バージョン管理システムと連携させ、「この修正コミットはこのバグに対応する」という関係を残すのが一般的な運用である。

誤答として並ぶ記述を確認すると、ツールの役割分担が整理できる。

| 記述 | 実際は何か |
| --- | --- |
| ソースコードを画面に表示しながら、プログラムの実行及び中断、変数の値の表示などの、バグの**発見を支援する**機能を提供する | **デバッガ** |
| テストケース及びテストプログラムの開発を支援して、バグの**発見を容易にする** | **テストツール** |
| バグの数とソースプログラムの諸元から、**品質管理のためのメトリクスを算定する** | **メトリクス測定ツール** |

**「発見」のデバッガとテストツール、「算定」のメトリクス測定ツール、「記録・管理」のバグトラッキングシステム**という3つの役割で区別できる。

> **出題** バグトラッキングシステム: R6午前II問25

## 3. デバッグ支援ツール

| ツール | 機能 |
| --- | --- |
| **デバッガ** | ブレークポイントで実行を止め、変数の値を確認しながら1行ずつ実行する |
| トレーサ | 実行経路や変数の変化を記録する |
| スナップショットダンプ | 指定した時点のメモリ内容を出力する |
| メモリダンプ | 異常終了時のメモリ全体を出力する |
| 静的解析ツール | 実行せずにソースコードを解析し、規約違反や潜在的な不具合を検出する |
| 逆アセンブラ | 機械語をアセンブリ言語に変換する |

これらの使い分けと、アサーションチェックとの違いは [12-3 実装・構築](../12-system-development/12-3-実装-構築.md) で詳しく扱う。

## 4. 自動化のツール

| ツール | 自動化する対象 |
| --- | --- |
| ビルドツール | コンパイル・リンク・パッケージング |
| **CI（継続的インテグレーション）ツール** | 変更のたびのビルドとテストの実行 |
| **CD（継続的デリバリ）ツール** | テスト済みのものを環境へ配置する作業 |
| プロビジョニングツール | サーバ構成の構築（→ [13-3 開発環境管理](../13-software-development-management/13-3-開発環境管理.md)） |
| テスト自動化ツール | 回帰テストの実行（→ [12-4 統合・テスト](../12-system-development/12-4-統合-テスト.md)） |

**CI/CDが重要なのは、「早く失敗する」ことを可能にするから**である。変更のたびに自動でビルドとテストが走れば、壊れた瞬間に気づける。まとめて統合する方式では、どの変更が原因かを切り分けるところから始めなければならない。[12-3 実装・構築](../12-system-development/12-3-実装-構築.md) で述べた「誤りの検出を前倒しする」という原則を、仕組みとして実現したものだといえる。

テスト自動化は、[12-6 保守・廃棄](../12-system-development/12-6-保守-廃棄.md) で見たリファクタリングの前提条件でもある。振る舞いが変わっていないことを機械的に確認できなければ、安心して内部構造に手を入れられない。

## この章のまとめ

- 開発ツールは**人がやると時間がかかり間違える作業を自動化する**ためにある。
- **バグトラッキングシステムは、バグの内容・発生バージョンを記録し、修正計画と履歴を管理する**。発見を支援するデバッガ・テストツール、品質指標を算定するメトリクス測定ツールとは役割が違う。
- **CI/CDは「早く失敗する」ための仕組み**。テスト自動化はリファクタリングの前提条件でもある。
