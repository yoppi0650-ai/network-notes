# 5-3 ファイルシステム

補助記憶装置上のデータを、**名前の付いた「ファイル」として扱えるようにする**仕組みを扱う。

ファイルシステムがなければ、プログラムは「ディスクの何セクタ目から何セクタ分」という物理的な位置を直接指定しなければならない。ファイルシステムはこれを**名前と階層構造による抽象化**に置き換える。利用者もプログラムも物理的な配置を知らずに済み、ディスクを入れ替えても同じように使える。

H21〜R7の午前I・午前IIでは**この小分類からの直接の出題は見当たらなかった**。ただし、バックアップ運用（→ [15-4 サービスの運用](../15-service-management/15-4-サービスの運用.md)）、ファイル共有プロトコル（→ [4-1 システムの構成](../04-system-components/4-1-システムの構成.md) のNAS）、アクセス権とデータ消去（→ [12-6 保守・廃棄](../12-system-development/12-6-保守-廃棄.md)）といった形で、関連する知識は他分野で問われている。

## 1. ファイルシステムの役割

| 役割 | 内容 |
| --- | --- |
| 名前付けと探索 | ファイル名からデータの格納位置を見つける |
| 領域の割当てと管理 | 空き領域を管理し、ファイルに割り当てる |
| アクセス制御 | 誰が何をしてよいかを管理する |
| 一貫性の維持 | 書込みの途中で電源が落ちても壊れないようにする（ジャーナリングなど） |

主記憶と同じく、ファイルシステムでも**フラグメンテーション**が問題になる（→ [5-1 オペレーティングシステム](5-1-オペレーティングシステム.md)）。ファイルの作成と削除を繰り返すと空き領域が細切れになり、1つのファイルが飛び飛びの位置に置かれる。磁気ディスクではヘッドの移動が増えて読み書きが遅くなるため、**デフラグ（最適化）**で連続化する。SSDでは機械的な移動がないので、デフラグの効果は小さく、むしろ書換え回数を消費して寿命を縮める（→ [3-2 メモリ](../03-computer-components/3-2-メモリ.md)）。

## 2. ディレクトリ

ファイルを階層的に整理する仕組みが**ディレクトリ（フォルダ）**である。

| 用語 | 意味 |
| --- | --- |
| ルートディレクトリ | 階層の最上位 |
| カレントディレクトリ | 現在作業しているディレクトリ |
| **絶対パス** | ルートディレクトリからの経路。`/home/user/data.txt` |
| **相対パス** | カレントディレクトリからの経路。`../data.txt`（`..` は親ディレクトリ） |

**相対パスの `..` を使った移動**が計算問題として問われることがある。カレントディレクトリから `..` で1つ上がり、そこから下りる、という操作を正確に追えばよい。

なお、Webアプリケーションで `../` を悪用して想定外のファイルを読み出す攻撃が**ディレクトリトラバーサル**である（→ [11-1 情報セキュリティ](../11-security/11-1-情報セキュリティ.md)）。ファイルシステムの仕組みがそのまま攻撃面になっている例といえる。

## 3. ファイルの編成

レコードをどう並べ、どう探すかで編成法が分かれる。

| 編成 | アクセス方法 | 特徴 |
| --- | --- | --- |
| 順編成 | 先頭から順に読む | 単純。磁気テープ向き（→ [3-5 入出力装置](../03-computer-components/3-5-入出力装置.md)） |
| 直接編成 | キーから格納位置を計算して直接読む | 高速。ハッシュ法と同じ原理（→ [2-1 データ構造](../02-algorithms-and-programming/2-1-データ構造.md)） |
| 索引編成 | 索引を引いてから目的のレコードを読む | 順アクセスと直接アクセスの両方ができる |
| 区分編成 | メンバごとに分け、ディレクトリで管理する | ライブラリの格納に使う |

この分類は、[2-1 データ構造](../02-algorithms-and-programming/2-1-データ構造.md) や [2-2 アルゴリズム](../02-algorithms-and-programming/2-2-アルゴリズム.md) で見た探索手法の対応関係とそのまま重なる。**順編成＝線形探索、索引編成＝2分探索やB木、直接編成＝ハッシュ**という具合で、「どう並べるかが、どう探せるかを決める」という原理は主記憶上のデータ構造でもファイルでも変わらない。データベースのインデックス（→ [9-2 データベース設計](../09-database/9-2-データベース設計.md)）も同じ系譜にある。

## 4. アクセス権とバックアップ

### 4.1 アクセス権

ファイルには、利用者やグループごとに**読取り・書込み・実行**の権限を設定する。

セキュリティの原則として、**必要最小限の権限だけを与える（最小権限の原則）**。開発環境で本番データに自由にアクセスできる状態が避けられるのも、この原則による（→ [13-3 開発環境管理](../13-software-development-management/13-3-開発環境管理.md)）。

### 4.2 バックアップ方式

| 方式 | 対象 | 復旧時の手間 |
| --- | --- | --- |
| **フルバックアップ** | 全データ | 1世代戻すだけ。最も簡単 |
| **差分バックアップ** | 前回の**フルバックアップ**以降に変更された分 | フル＋最新の差分の2つ |
| **増分バックアップ** | 前回の**バックアップ（種類を問わず）**以降に変更された分 | フル＋すべての増分。最も手間がかかる |

**差分と増分の違いは「どこからの変更か」**である。差分は常にフルバックアップからの変更を取るので、日が経つほどバックアップ自体は大きくなるが、復旧は2つ戻せば済む。増分は毎回前回からの変更だけなので取得は速くて小さいが、復旧にはすべてを順に適用する必要がある。

**取得コストと復旧コストのトレードオフ**であり、どちらを選ぶかは目標復旧時間（RTO）と目標復旧時点（RPO）から決まる（→ [11-2 情報セキュリティ管理](../11-security/11-2-情報セキュリティ管理.md)）。バックアップ運用に必要な媒体数を求める計算問題は [15-4 サービスの運用](../15-service-management/15-4-サービスの運用.md) で扱う。

### 4.3 データの消去

ファイルを「削除」しても、**多くのファイルシステムは管理情報を消すだけで、データの実体は残る**。だから復元ソフトで読み出せてしまう。記憶媒体を廃棄・再利用する際には、上書き消去や物理破壊によって確実に読み出せない状態にする必要がある（→ [12-6 保守・廃棄](../12-system-development/12-6-保守-廃棄.md)）。

## この章のまとめ

- ファイルシステムは**物理的な配置を名前と階層で抽象化する**仕組み。フラグメンテーションの問題は主記憶管理と同じ構造をもつ。
- ファイルの編成法は、**どう並べるかが、どう探せるかを決める**という原理でデータ構造・探索アルゴリズムと対応している。
- バックアップは**差分＝フルからの変更（復旧が簡単）、増分＝前回からの変更（取得が軽い）**。取得コストと復旧コストのトレードオフになる。
- **削除してもデータの実体は残る**。廃棄時には確実な消去が必要になる。
