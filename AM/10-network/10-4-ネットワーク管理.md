# 10-4 ネットワーク管理

ネットワークは作って終わりではない。動かし続けるには、**今どうなっているかを知る**手段と、**異常に気づく**手段が要る。この章では、その中心となるSNMPを軸に、ネットワーク運用管理の考え方とツールを扱う。

午前IIからの直接の出題は16年間で2問と多くないが、いずれもSNMP関連であり、SDNの設問の誤答選択肢にもSNMPやsFlowが頻繁に登場する（→ [10-1](10-1-ネットワーク方式.md)）。また午後試験では運用管理が主題になることも多い。設問数の割に押さえておく価値が高い分野である。

出題が少ないぶん、本章では試験に直接出た内容に加えて、**技術を理解するために必要な前提知識**を補っている。どこまでが過去問由来かは節末の「出題」で確認してほしい。

## 1. ネットワーク管理の対象

ネットワーク管理の機能は、OSIの管理機能分類（FCAPS）として5つに整理されている。

| 機能 | 内容 |
| --- | --- |
| **障害管理** (Fault) | 障害の検知・切り分け・復旧。ログやトラップの監視 |
| **構成管理** (Configuration) | 機器構成・接続構成・設定情報の把握と変更管理 |
| **課金管理** (Accounting) | 利用量の計測と課金 |
| **性能管理** (Performance) | トラフィック量・応答時間・使用率の測定と傾向分析 |
| **セキュリティ管理** (Security) | アクセス権の管理、不正アクセスの検知 |

このうち試験で中心になるのは**障害管理と性能管理**である。どちらも「機器から情報を集める」ことが出発点になるため、収集の仕組みであるSNMPが要になる。

## 2. SNMP

**SNMP（Simple Network Management Protocol）**は、ネットワーク機器の状態を収集・設定するためのプロトコルである。UDPを使い、**ポート161（問合せ）**と**ポート162（トラップ）**を使い分ける。

構成要素は2つである。

| 役割 | 位置 | 仕事 |
| --- | --- | --- |
| **マネージャ** | 管理用のサーバ | エージェントに問い合わせ、情報を収集・表示する |
| **エージェント** | ルータ、スイッチ、サーバなど管理される側 | 自分の状態を**MIB**として保持し、問合せに答える |

### 2.1 メッセージタイプ

SNMPv1 のメッセージは5種類ある。**誰が誰に、いつ送るか**で整理する。

| メッセージ | 方向 | 内容 |
| --- | --- | --- |
| get-request | マネージャ → エージェント | 指定したMIB情報の取得を要求する |
| get-next-request | マネージャ → エージェント | 次のMIB情報を要求する（ツリーを順に辿る） |
| get-response | エージェント → マネージャ | 要求への応答 |
| set-request | マネージャ → エージェント | MIB情報の変更を要求する（設定変更） |
| **trap** | **エージェント → マネージャ** | **異常や事象の発生を、エージェント自身が自発的にマネージャに知らせる** |

**trap だけが向きも契機も異なる**。他の4つは「マネージャが尋ね、エージェントが答える」ポーリング型のやり取りだが、trapは**エージェント発の自発的な通知**である。

この違いには理由がある。ポーリングだけに頼ると、障害を知るのは次のポーリングのときになる。間隔を5分にすれば発見は最大5分遅れ、間隔を短くすれば監視トラフィックと機器の負荷が増える。trapは「異常が起きた瞬間にエージェントから知らせる」ことでこのジレンマを解消する。実運用では、**trapで即座に気づき、ポーリングで継続的に傾向を把握する**という併用が基本になる。

ただしtrapはUDPで送られるため、途中で失われてもエージェントは気づかない。この弱点を補うため、SNMPv2 では応答を伴う **inform** が追加された。

### 2.2 バージョン

| 版 | 認証・暗号化 |
| --- | --- |
| SNMPv1 | **コミュニティ名**（平文の合言葉）だけ |
| SNMPv2c | v1と同じくコミュニティ名。get-bulk、informなどを追加 |
| **SNMPv3** | **利用者認証と暗号化**に対応 |

v1/v2cのコミュニティ名は平文で流れるため、盗聴されれば機器情報を読まれ、set-requestで設定を書き換えられる恐れすらある。管理用ネットワークを分離するか、SNMPv3を使うのが望ましい。

> **出題** SNMPのメッセージタイプ（trap）: H22午前II問17

## 3. MIB

**MIB（Management Information Base）**は、エージェントが公開する管理情報の集合であり、**ツリー構造で体系化**されている。各項目には **OID（オブジェクト識別子）**という数値の並びが付けられ、`1.3.6.1.2.1.1.3`（システムの稼働時間）のように指定する。

ツリー構造になっているのは、**メーカや機種が違っても共通の場所に共通の情報がある**ようにするためである。標準化された部分（MIB-II）には、インタフェースの送受信バイト数・エラー数・稼働状態といった、どの機器にもある情報が定義されている。一方、メーカ独自の情報は**プライベートMIB**として別の枝にぶら下げる。これにより、汎用の監視ツールで多ベンダの機器を一様に監視しつつ、必要なら機種固有の情報も拾える。

性能管理の実務では、MIBからインタフェースの累積送受信バイト数を定期的に取得し、**差分を取得間隔で割って**トラフィック量（ビット/秒）を算出する、という使い方をする。

## 4. RMONとフロー監視

### 4.1 RMON

MIBから得られるのは「このポートを何バイト通ったか」という**量**の情報だけである。「誰が誰と、どんな通信をしていたのか」という**中身**はわからない。混雑の原因を突き止めるにはこれでは足りない。

**RMON（Remote Network MONitoring）**はこの隙間を埋める。

> **測定対象の回線やポートなどからパケットをキャプチャして解析し、SNMPを使って管理装置にデータを送信する仕組み**

RMONプローブ（専用機器、またはスイッチの機能）が実際のパケットを観測して統計を取り、その結果をRMON MIBとして保持する。マネージャはそれを通常のSNMPで取得する。つまり**解析はプローブ側で行い、結果だけをSNMPで運ぶ**という分担になっている。パケットそのものを管理サーバまで運ぶと帯域を食いつぶすので、現場で集計するわけである。

用語の関係を整理しておく。

| 用語 | 位置づけ |
| --- | --- |
| SNMP | 情報を**運ぶプロトコル** |
| MIB | 運ばれる**情報の構造** |
| RMON | パケットを解析して統計を作る**仕組み**（結果はMIBとして保持し、SNMPで運ぶ） |
| Trap | エージェント発の**通知メッセージ** |

### 4.2 sFlow / NetFlow

**sFlow** や **NetFlow** は、**フロー（送信元/宛先IPアドレスとポート番号の組合せ）ごとの統計情報を、ネットワーク機器がコレクタと呼ばれるサーバに送信する**仕組みである。SDNの設問で誤答選択肢として登場する（→ [10-1](10-1-ネットワーク方式.md)）。

RMONが「プローブが観測して統計を保持し、マネージャが取りに来る」のに対し、sFlow/NetFlowは「機器が自発的にコレクタへ送る」点が異なる。大規模ネットワークのトラフィック分析では後者が主流である。

> **出題** RMON: R4午前II問14

## 5. その他の管理の仕組み

| 仕組み | 役割 |
| --- | --- |
| **syslog** | 機器のログを集約サーバへ送る。UDP 514 |
| **NTP** | 機器の時刻を同期する。UDP 123。ログの時刻が揃っていないと障害の因果関係を追えないため、管理の前提になる |
| ICMP (ping) | 死活監視の最も簡便な手段 |

NTPは時刻合わせという地味な機能だが、複数機器のログを突き合わせて障害を追跡するうえで不可欠である。一方でNTPサーバは**増幅型DDoS攻撃の踏み台にされる**という問題も抱えている（→ [11-4 情報セキュリティ対策](../11-security/11-4-情報セキュリティ対策.md)）。

## 6. ネットワーク管理コマンド

障害の切り分けは、**下の層から順に確認する**のが鉄則である。「ケーブルは挿さっているか → IPアドレスは正しいか → 相手まで届くか → 名前は引けるか → サービスは応答するか」と順に潰していく。各段階に対応するコマンドがある。

| コマンド | 確認できること |
| --- | --- |
| `ipconfig` / `ifconfig` / `ip addr` | 自分のIPアドレス、サブネットマスク、デフォルトゲートウェイ |
| `ping` | ICMPによる相手の到達性と往復時間 |
| `traceroute` / `tracert` | 相手までの経路（通過するルータ）。TTLを1ずつ増やしてICMP Time Exceededを集める |
| `arp -a` | ARPテーブル（IPアドレスとMACアドレスの対応） |
| `netstat` / `ss` | 自分のコネクション状態、待ち受けポート、ルーティングテーブル |
| `nslookup` / `dig` | DNSの名前解決結果 |
| `tcpdump` / Wireshark | パケットキャプチャ。最終手段だが最も情報量が多い |

`traceroute` がTTLを使う仕組みは ICMP の理解がそのまま応用されたものである（→ [10-3](10-3-通信プロトコル.md)）。TTLを1にしたパケットは1台目のルータで破棄され、そのルータからTime Exceededが返ってくる。TTLを2にすれば2台目から返ってくる。これを繰り返せば経路上のルータが順に判明する。

## この章のまとめ

- ネットワーク管理の5機能は**障害・構成・課金・性能・セキュリティ**。中心は障害管理と性能管理。
- **SNMPはマネージャとエージェント**の間で情報をやり取りする。**trapだけがエージェント発の自発的通知**で、他はマネージャからの問合せとその応答である。
- **MIBは管理情報のツリー構造**。標準部分で多ベンダを一様に監視し、プライベートMIBで機種固有情報を扱う。
- **RMONはパケットをキャプチャして解析し、結果をSNMPで管理装置に送る**仕組み。SNMPは運搬役、MIBは構造、RMONは解析役と役割が違う。
- 障害の切り分けは**下の層から順に**。`ping` → `traceroute` → `nslookup` → パケットキャプチャ。
