# 11-3 セキュリティ技術評価

セキュリティ対策を「やったつもり」で終わらせないために、**本当に守れているかを確かめる**技術と制度を扱う。

実装にはどうしても想定漏れが残る。設計書どおりに作ってもコードにバグが残り、既知の脆弱性に対するパッチを当て忘れ、設定が意図どおりになっていないことがある。それを**作った側とは別の視点で突っつく**のがセキュリティ技術評価である。

午前Iから断続的に出題される。設問数は少ないが、**検査手法の名前と「何に注目して何を見つけるか」の対応**は確実に押さえたい。

出題が少ない分野のため、本章では過去問で問われた手法に加えて、理解に必要な評価制度の知識を補っている。

## 1. 脆弱性検査の手法

検査手法は**何に注目するか**で分類できる。

| 手法 | 注目する対象 | 見つけるもの |
| --- | --- | --- |
| **ファジング** | **データの入出力** | 想定外の入力に対する異常な挙動 |
| **ペネトレーションテスト** | システム全体 | 実際に侵入できてしまうかどうか |
| ソースコード検査（静的解析） | ソフトウェアの内部構造 | ソースコードの構文上の問題 |
| バージョン・パッチ検査 | 導入済みソフトウェアの版 | 既知の脆弱性への未対応 |
| セキュリティ情報の確認 | ベンダや関連機関のアドバイザリ | 新たに公表された脆弱性 |

### 1.1 ファジング

**ファジング（fuzzing）**は、

> **ソフトウェアのデータの入出力に注目し、問題を引き起こしそうなデータを大量に多様なパターンで入力して挙動を観察し、脆弱性を見つける**

手法である。「ファズ（fuzz）」と呼ばれる無効・予期しない・ランダムなデータを機械的に投入し、クラッシュ・ハングアップ・メモリリークといった異常が起きないかを監視する。

この手法が有効なのは、**開発者が想定していない入力こそが脆弱性の温床だから**である。極端に長い文字列、負の数、制御文字、不正な文字コード、境界値を少し超えた値──こうした入力は仕様書に書かれていないので、テストケースにも含まれにくい。しかしバッファオーバフローや入力検証漏れはまさにそこで起きる。人間が思いつく範囲を機械の物量で超えるのがファジングの発想である。

**ソースコードを必要としないブラックボックス検査**であり、仕様書がなくても実行できる点も実用上の利点になる。

誤答として並ぶ手法と区別する。

| 記述 | 実際は何か |
| --- | --- |
| サーバにFINパケットを送信し、応答を観測して稼働サービスを見つけ出す | **ポートスキャン**（FINスキャン） |
| ログやコマンド履歴を解析してファイルの改ざんを検知する | 改ざん検知・ログ監査 |
| パケットを収集し、登録された攻撃パターンと一致したら不正アクセスと判断する | **シグネチャ型のIDS/IPS**（→ [11-4](11-4-情報セキュリティ対策.md)） |
| 導入ソフトのバージョンとパッチ適用状況を検査する | 既知脆弱性の対応状況検査 |
| ソースコードの構文をチェックして脆弱性を見つける | **静的解析（ホワイトボックス検査）** |

### 1.2 ペネトレーションテスト

**ペネトレーションテスト（侵入テスト）**の目的は、

> **ファイアウォールや公開サーバに対して侵入できないかどうかを確認する**

ことである。検査者が攻撃者の立場で**実際にシステムを攻撃して侵入を試みる**。

脆弱性スキャナによる機械的な検査が「既知の弱点が残っていないか」を網羅的に調べるのに対し、ペネトレーションテストは**複数の弱点を組み合わせて実際に到達できるか**を確かめる。単体では軽微な問題でも、連鎖すれば重大な侵入経路になりうる。それを人間の発想で見つけるのが価値である。

誤答に並ぶのは、いずれも「確認する」という言葉は同じだが目的が違うものである。

- 暗号方式と鍵長が設計仕様と一致するかの確認 → 設計適合性の検証
- 入力に対する出力結果が出力仕様と一致するかの確認 → 機能テスト（→ [12-4 統合・テスト](../12-system-development/12-4-統合-テスト.md)）
- ファイアウォールが単位時間当たりに処理できるセッション数の確認 → 性能テスト

**実施には必ず対象システムの所有者の許可が要る**。同じ行為を無断で行えば不正アクセス禁止法に触れる（→ [23-2 セキュリティ関連法規](../23-legal-affairs/23-2-セキュリティ関連法規.md)）。

> **出題** ファジング: H30午前I問15、R1午前I問14、R4午前I問15 ｜ ペネトレーションテスト: H27午前I問15

## 2. ポートスキャン

**ポートスキャン**は、対象ホストのどのポートが開いているか（どのサービスが動いているか）を調べる手法である。脆弱性検査の初手として使われる一方、攻撃の偵察にも使われる。

判定の原理は**プロトコルの正常な応答を利用する**ことにある。TCPとUDPで応答の性質が異なるため、判定方法も変わる。

### 2.1 TCPポートの判定

TCPは3ウェイハンドシェイクを行う（→ [10-3](../10-network/10-3-通信プロトコル.md)）。この応答が手がかりになる。

| 送るもの | 返ってくるもの | 判定 |
| --- | --- | --- |
| SYN | **SYN/ACK** | **ポートが開いている（接続要求が許可された）** |
| SYN | **RST/ACK** | **ポートが閉じている（接続要求が拒否された）** |
| SYN | 無応答 | ファイアウォールで遮断されている可能性 |

誤答はこの2つを入れ替えてくる。**SYN/ACK は「どうぞ接続してください」という正常な応答なので開いている**、**RST はコネクションの強制リセットなので閉じている**、と意味から考えれば取り違えない。

3ウェイハンドシェイクを完了させずにSYN/ACKを受け取った時点でRSTを送って中断する手法を **SYNスキャン（ハーフオープンスキャン）**といい、接続ログが残りにくいため検知されにくい。

### 2.2 UDPポートの判定

UDPはコネクションレスなので（→ [10-3](../10-network/10-3-通信プロトコル.md)）、開いていても応答が返るとは限らない。そこで**閉じているときの応答**を利用する。

| 送るもの | 返ってくるもの | 判定 |
| --- | --- | --- |
| UDPパケット | **ICMP port unreachable** | **ポートが閉じている** |
| UDPパケット | 無応答、またはサービスからの応答 | 開いている可能性が高い |

**「ICMP port unreachable を受信したら閉じている」**が正しい。これは「そのポートで待ち受けているプログラムがいません」という通知だからである。開いているかどうかを直接確かめられないので、**閉じていることを確認できなかったポートを「開いている可能性がある」と推定する**という、消去法的な判定になる。この不確実さがUDPスキャンの難しさである。

> **出題** ポートスキャンによる判定: R1午前II問19

## 3. 脆弱性の評価指標と情報源

発見された脆弱性は、共通の尺度で評価し、共通の識別子で呼べるようにしておかないと、対応の優先順位を付けられない。そのための仕組みが整備されている。

| 仕組み | 内容 |
| --- | --- |
| **CVE** (Common Vulnerabilities and Exposures) | 個別の脆弱性に付ける**共通の識別番号**（例：CVE-2024-12345） |
| **CVSS** (Common Vulnerability Scoring System) | 脆弱性の深刻度を**0.0〜10.0のスコア**で表す共通の評価手法 |
| **CWE** (Common Weakness Enumeration) | 脆弱性の**種類**（バッファオーバフロー、XSSなど）の共通分類 |
| **JVN** (Japan Vulnerability Notes) | JPCERT/CCとIPAが運営する**日本の脆弱性情報ポータル** |

**CVSS** は3つの基準でスコアを算出する。

| 基準 | 評価するもの |
| --- | --- |
| 基本評価基準 (Base) | 脆弱性そのものの特性。攻撃の容易さ、影響範囲。時間が経っても変わらない |
| 現状評価基準 (Temporal) | 攻撃コードの出回り具合、対策の有無。時間とともに変化する |
| 環境評価基準 (Environmental) | 利用者の環境における重要度。組織ごとに異なる |

同じ脆弱性でも、攻撃コードが公開されれば危険度は上がり、自組織で使っていない機能なら重要度は下がる。**「脆弱性の深刻度」は固定値ではなく文脈で変わる**という考え方がCVSSの基本にある。

## 4. 製品・組織の評価制度

| 制度 | 対象 |
| --- | --- |
| **ISO/IEC 15408（コモンクライテリア、CC）** | **IT製品・システムのセキュリティ機能**を評価・認証する国際規格。評価保証レベル EAL1〜EAL7 で表す |
| **JISEC** | 日本におけるIT製品のセキュリティ評価・認証制度（ISO/IEC 15408に基づく） |
| **JCMVP** | 暗号モジュールの試験・認証制度 |
| **ISMS適合性評価制度** | **組織のマネジメントシステム**（JIS Q 27001）を認証する（→ [11-2](11-2-情報セキュリティ管理.md)） |
| **PCI DSS** | クレジットカード業界の情報セキュリティ基準。カード会員データを扱う事業者が対象 |
| プライバシーマーク | 個人情報の取扱いが適切な事業者を認定する（JIS Q 15001に基づく） |

評価の対象が**「製品」なのか「組織」なのか**で大きく分かれる点を押さえる。コモンクライテリアは製品のセキュリティ機能を、ISMS適合性評価制度は組織の運用体制を評価する。両者は補完関係にあり、認証された製品を使っても運用がずさんなら守れないし、逆もまた同じである。

## この章のまとめ

- **ファジングは「データの入出力に注目し、問題を起こしそうなデータを大量・多様に入力して挙動を観察する」**。ソースコード不要のブラックボックス検査。
- **ペネトレーションテストは「実際に攻撃して侵入できるかを確認する」**。機械的なスキャンでは見つからない、弱点の連鎖を見つけるのが価値。実施には許可が必須。
- ポートスキャンの判定は、**TCPは SYN/ACK なら開、RST なら閉**。**UDPは ICMP port unreachable が返ったら閉**。
- 脆弱性は **CVE（識別番号）／CVSS（深刻度スコア）／CWE（種類の分類）／JVN（国内の情報源）**で整理されている。CVSSは基本・現状・環境の3基準で、文脈によって値が変わる。
- 評価制度は対象で分かれる。**コモンクライテリア（ISO/IEC 15408）は製品、ISMS適合性評価制度は組織**。
