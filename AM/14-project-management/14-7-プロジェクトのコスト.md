# 14-7 プロジェクトのコスト

費用を見積り、予算を組み、支出を管理する領域を扱う。

この分野の中心は2つある。**開発規模の見積り**（どれだけの作業量か）と、**EVM による進捗とコストの統合管理**（計画どおり進んでいるか）である。前者はプロジェクトの出発点、後者は実行中の舵取りにあたる。

## 1. 開発規模と工数の関係

> ソフトウェアの**開発規模と開発工数の関係**を表すグラフはどれか。

正解は、**規模が大きくなるほど、工数が規模の増加割合を上回って増える**曲線（下に凸の右上がり）である。

```
開発工数
  │                          ／
  │                     ／
  │               ／
  │        ／
  │   ／
  └──────────────────────→ 開発規模
```

**比例（直線）にならない**のがこの問題の要点である。規模が2倍になっても工数は2倍では済まない。理由は [14-5 プロジェクトの資源](14-5-プロジェクトの資源.md) で見た人的資源の性質にある。

- 規模が大きくなれば必要な要員が増える
- 要員が増えれば**コミュニケーションの経路が $n(n-1)/2$ で増える**（→ [14-11 プロジェクトのコミュニケーション](14-11-プロジェクトのコミュニケーション.md)）
- 調整と情報共有の負荷が、作業そのものより速く増えていく

この非線形性が、大規模プロジェクトが小規模プロジェクトの単純な延長にならない理由であり、見積り手法が経験則に頼らざるをえない理由でもある。

> **出題** 開発規模と開発工数の関係: H21午前I問19

## 2. 見積り手法

| 手法 | 根拠 |
| --- | --- |
| **ファンクションポイント法（FP法）** | **ソフトウェアの機能量** |
| LOC法（Lines of Code） | ソースコードの行数 |
| **COCOMO** | 開発規模（LOC）と補正係数から工数を算出する数式モデル |
| **Putnamモデル** | 工数と期間の関係を数式で表したモデル |
| **Dotyモデル** | 開発規模から工数を算出する数式モデル |
| 類推法 | 過去の類似プロジェクトの実績から推定する |
| 標準タスク法（積上げ法） | WBSの作業ごとに積み上げる |
| デルファイ法 | 複数の専門家の見積りを収束させる（→ [20-1 技術開発戦略の立案](../20-technology-strategy-management/20-1-技術開発戦略の立案.md)） |

### 2.1 ファンクションポイント法

> アプリケーションにおける**外部入力、外部出力、内部論理ファイル、外部インタフェースファイル、外部照会**の五つの要素の個数を求め、それぞれを重み付けして集計する。集計した値がソフトウェア開発の規模に相関するという考え方に基づいて、開発規模の見積りに利用されるものはどれか。

答えは**ファンクションポイント法**である。5つの要素は丸ごと覚えておきたい。

| 要素 | 内容 |
| --- | --- |
| 外部入力 (EI) | 外部からのデータ入力 |
| 外部出力 (EO) | 外部へのデータ出力 |
| 外部照会 (EQ) | 入力に対する単純な検索と出力 |
| 内部論理ファイル (ILF) | システム内部で保持するデータ |
| 外部インタフェースファイル (EIF) | 他システムから参照するデータ |

**調整前FP**を求めるために必要な情報は、

> **画面数**

である。

| 情報 | 必要か |
| --- | --- |
| **画面数** | **必要**。画面は外部入力・外部出力・外部照会の数に直結する |
| 開発者数 | 不要。FP法は**作る人ではなく作るものの量**を測る |
| **プログラムステップ数** | 不要。むしろ**ステップ数を使うのがLOC法**であり、FP法はそれを避けるために考案された |
| 利用者数 | 不要。利用者が何人いても機能量は変わらない |

**FP法がLOC法より優れているとされるのは、開発言語や実装方法に依存しないから**である。同じ機能でも、言語を変えればステップ数は大きく変わる。しかし**利用者から見える機能の量は変わらない**。だから要件定義の段階、すなわちコードを1行も書いていない時点でも見積れる。これが実務上の最大の利点になる。

### 2.2 数式モデル

**COCOMO**、**Putnamモデル**、**Dotyモデル**は、いずれも**規模から工数を算出する数式モデル**である。FP法が「規模を測る」手法であるのに対し、これらは「規模から工数を導く」手法という違いがある。設問ではFP法の誤答選択肢として並ぶ。

> **出題** ファンクションポイント法: H23午前I問19、H30午前I問19

## 3. EVM

**EVM（アーンドバリューマネジメント）**は、**進捗とコストを同じ「金額」の尺度で測る**手法である。**5回以上出題されている**最重要テーマである。

> プロジェクト管理においてパフォーマンス測定に使用する **EVM の管理対象**の組みはどれか。

答えは **コスト、スケジュール**である。品質やリスクは対象外である。

### 3.1 3つの基本量

| 略語 | 名称 | 意味 |
| --- | --- | --- |
| **PV** (Planned Value) | 計画価値 | **その時点までに完了している予定**だった作業の、予算額 |
| **EV** (Earned Value) | 出来高 | **実際に完了した**作業の、予算額 |
| **AC** (Actual Cost) | 実コスト | 実際に**かかった**費用 |
| **BAC** (Budget At Completion) | 完成時総予算 | プロジェクト全体の予算 |

EVMの核心は、**EV（出来高）を「予算額で評価した進捗」として表す**ところにある。「作業が何%終わったか」という主観的な報告ではなく、「予算100万円分の作業のうち40万円分が終わった」と金額で表すので、コストと直接比較できる。

### 3.2 差異と効率指数

| 指標 | 式 | 意味 |
| --- | --- | --- |
| **CV**（コスト差異） | $EV - AC$ | **正なら予算内、負なら超過** |
| **SV**（スケジュール差異） | $EV - PV$ | **正なら前倒し、負なら遅延** |
| **CPI**（コスト効率指数） | $EV \div AC$ | **1より大きければ効率がよい** |
| **SPI**（スケジュール効率指数） | $EV \div PV$ | **1より大きければ前倒し** |

**どちらもEVを基準に、ACと比べればコスト、PVと比べればスケジュール**という構造になっている。「EVがいくらの作業を終えたか」に対して、「いくら使ったか（AC）」「いくら使う予定だったか（PV）」を突き合わせる、と理解すれば式を覚える必要がない。

```
         EV（出来高）
        ／        ＼
   ÷ AC            ÷ PV
  （実コスト）     （計画価値）
      ↓               ↓
     CPI             SPI
   コスト効率     スケジュール効率
```

> **出題** EVMの管理対象: H24午前I問19、H27午前I問18、H29午前I問18（計3回）

## 4. EVMによる予測と評価

### 4.1 完成時総コスト見積り（EAC）

> 期間10日間のプロジェクトの5日目終了時点の状況は次のとおりである。この時点での**コスト効率が今後も続くとしたとき、完成時総コスト見積り（EAC）**は何万円か。
>
> | 管理項目 | 金額（万円） |
> | --- | --- |
> | 完成時総予算（BAC） | 100 |
> | 計画価値（PV） | 50 |
> | 出来高（EV） | 40 |
> | 実コスト（AC） | 60 |

**「現在のコスト効率が今後も続く」場合のEAC**は、

$$ EAC = \frac{BAC}{CPI} $$

で求まる。まずCPIを計算する。

$$ CPI = \frac{EV}{AC} = \frac{40}{60} = \frac{2}{3} $$

したがって

$$ EAC = \frac{100}{2/3} = 100 \times \frac{3}{2} = \mathbf{150\ \text{万円}} $$

**式の意味**を押さえておくと忘れない。CPIが $2/3$ ということは、**60万円使って40万円分の価値しか生めていない**、つまり予算の1.5倍のコストがかかっている。この調子で最後まで行けば、総予算100万円の作業に $100 \times 1.5 = 150$ 万円かかる、という計算である。

この時点の状況を整理すると、

- $CV = EV - AC = 40 - 60 = -20$ → **20万円の予算超過**
- $SV = EV - PV = 40 - 50 = -10$ → **10万円分の作業が遅れている**

**コストも進捗も計画を下回っている**状態である。

### 4.2 グラフからの読み取り

> EVMで管理しているプロジェクトの、開始から完了予定までの期間の半分が経過した時点での状況がグラフで示されている。**コスト効率、スケジュール効率がこのままで推移する**と仮定した場合の見通しはどれか。

グラフでは、横軸が時間、縦軸が金額で、PV・EV・AC の3本の曲線が描かれる。読み取りの手順は次のとおりである。

| 比較 | 読み取り |
| --- | --- |
| **EV と AC** | **EV < AC なら予算超過**（同じ出来高により多く使っている） |
| **EV と PV** | **EV < PV なら進捗が遅れている** |

遅れているなら**完了は遅くなり**、予算を超過しているなら**コストは多くなる**。グラフ上でACが最も上、次にPV、最も下にEVという並びなら、**「計画に比べてコストは多くなり、プロジェクトの完了は遅くなる」**という見通しになる。

**縦の比較（同じ時点での金額の差）**で判断するのが読み方の基本である。

### 4.3 TCPIと総合評価

**TCPI（残作業効率指数）**は、**残りの作業を予算内に収めるために必要なコスト効率**である。1より大きければ、**今より効率を上げなければ予算に収まらない**ことを意味する。

> EVMを使用してマネジメントをしているプロジェクトで、進捗に関する指標値は次のとおりであった。このプロジェクトに対する適切な評価と対策はどれか。
>
> - **CPI（コスト効率指数）：0.9**
> - **SPI（スケジュール効率指数）：1.1**
> - **BACに基づくTCPI（残作業効率指数）：1.2**

3つの指標を順に読む。

| 指標 | 値 | 読み取り |
| --- | --- | --- |
| CPI | **0.9**（< 1） | **コストが予算を超えている** |
| SPI | **1.1**（> 1） | **スケジュールには余裕がある**（前倒し） |
| TCPI | **1.2**（> 1） | **残作業は、今より効率を上げなければ予算に収まらない** |

したがって正しい評価と対策は、

> **コストが予算を超えているので、完成時総予算を超過するおそれがあるが、スケジュールには余裕があるので、残作業のコスト効率を上げる対策を検討するか、コンティンジェンシー予備費の使用を検討する。**

**3つの指標がそれぞれ別のことを言っている**点を正確に読み分けるのがこの設問の狙いである。「コストは超過、スケジュールは良好、残りは効率改善が必要」という3点がそろって初めて、この選択肢になる。CPIとSPIのどちらが1を下回っているかを取り違えた選択肢が並ぶので、**1より大きいか小さいかを機械的に確認する**のが確実である。

対策の選択肢として挙がる**コンティンジェンシー予備費**は、特定できたリスクに備えてあらかじめ確保しておく予備費である（→ [14-8 プロジェクトのリスク](14-8-プロジェクトのリスク.md)）。

なお、スケジュールが遅れている場合の対策として挙がる**ファストトラッキング**や**クラッシング**は [14-6 プロジェクトの時間](14-6-プロジェクトの時間.md) で扱う。この設問ではスケジュールに余裕があるので、これらは不要である。

> **出題** EVM・完成時総コスト見積り: H21午前I問18、R4午前I問18 ｜ EVMによる見通し: R6午前I問18 ｜ EVMの指標: R7午前I問18

## この章のまとめ

- **開発規模と工数の関係は比例ではなく、規模が増えるほど工数の増加が加速する**。コミュニケーションの負荷が $n(n-1)/2$ で増えるため。
- **ファンクションポイント法は機能量で測る**ので、言語や実装に依存せず、要件定義の段階で見積れる。必要な情報は**画面数**であり、ステップ数や開発者数ではない。
- EVMの管理対象は**コストとスケジュール**。**EVを基準に、ACと比べればコスト、PVと比べればスケジュール**。
- **$CPI = EV/AC$、$SPI = EV/PV$、$EAC = BAC/CPI$**。1より大きいか小さいかで良否を判断する。
- **TCPIが1より大きければ、今より効率を上げないと予算に収まらない**。
- グラフは**同じ時点での縦の比較**で読む。**EV < AC なら予算超過、EV < PV なら遅延**。
