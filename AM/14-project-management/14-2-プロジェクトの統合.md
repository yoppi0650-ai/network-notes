# 14-2 プロジェクトの統合

プロジェクト全体を**ひとつにまとめて動かす**ための管理を扱う。個々の領域（スコープ、時間、コスト、品質…）の管理を調整し、全体として辻褄が合うようにするのが統合マネジメントである。

統合が独立した領域になっているのは、**個別最適が全体最適にならない**からである。品質を上げればコストが増え、納期を守ろうとすればスコープを削ることになる。どれを優先するかを決められるのは、全体を見ている立場だけである。本章で扱うプロジェクト憲章と統合変更管理は、その「全体を見る」仕組みにあたる。

午前Iの問18前後から出題される。16年で2問。

## 1. プロジェクト憲章

> プロジェクトマネジメントにおける**「プロジェクト憲章」**の説明はどれか。

答えは、

> **プロジェクトを正式に認可するために、ビジネスニーズ、目標、成果物、プロジェクトマネージャ、及びプロジェクトマネージャの責任・権限を記した文書。**

キーワードは**「正式に認可する」「プロジェクトマネージャの責任・権限」**である。

プロジェクト憲章が必要な理由は、**プロジェクトマネージャに正統性を与える**ことにある。プロジェクトは既存の組織構造をまたいで人や資源を使うので、「誰の権限でこれをやっているのか」が曖昧だと動けない。憲章は組織の上位者（スポンサー）が発行し、**「このプロジェクトを承認し、この人に権限を与える」と宣言する文書**である。

したがって憲章は**計画より前、立上げの段階で作られる**（→ [14-1 プロジェクトマネジメント](14-1-プロジェクトマネジメント.md)）。計画を立てるには権限と目標が先に要るからである。

## 2. 主要文書の区別

プロジェクトの主要文書は、**何を定めるか**で区別する。設問ではこれらの説明が入れ替えられる。

| 文書 | 定めるもの |
| --- | --- |
| **プロジェクト憲章** | **プロジェクトを正式に認可する**。ビジネスニーズ、目標、成果物、プロジェクトマネージャの責任・権限 |
| **プロジェクトマネジメント計画書** | **プロジェクトの実行、監視、管理の方法を規定する**。スケジュール、リスクなどに関するマネジメントの役割や責任 |
| **プロジェクトスコープ記述書** | **プロジェクトのスコープを定義する**。プロジェクトの目標、成果物、要求事項及び境界（→ [14-4 プロジェクトのスコープ](14-4-プロジェクトのスコープ.md)） |
| **WBS** | **プロジェクトで実行する作業を階層構造で記す**（→ [14-4](14-4-プロジェクトのスコープ.md)） |

4つは**抽象から具体への順**に並んでいる。

```
プロジェクト憲章      「やることを認める。責任者はこの人」
  ↓
スコープ記述書        「何を作り、何を作らないか」
  ↓
WBS                   「そのためにどんな作業が要るか」
  ↓
マネジメント計画書    「それをどう管理するか」
```

**憲章が「認可」、スコープ記述書が「範囲」、WBSが「作業の分解」、計画書が「管理の方法」**と、一語で紐付けておけば取り違えない。

> **出題** プロジェクト憲章: R5午前I問18

## 3. 統合変更管理

プロジェクトでは変更が必ず発生する。要求が変わり、見積りが外れ、前提が崩れる。これを統制するのが**統合変更管理プロセス**である。

> PMBOKの統合変更管理プロセスにおいて、プロジェクトのプロダクト、サービス、所産、構成要素などに対する**変更と実施状況を記録・報告したり、要求事項への適合性を検証する活動を支援したりする活動**はどれか。

答えは **コンフィギュレーション・マネジメント（構成マネジメント）**である。

この活動が担うのは次の3つである。

| 機能 | 内容 |
| --- | --- |
| 構成の識別 | 何が成果物を構成しているかを特定する |
| 構成の状況記録 | **変更と実施状況を記録・報告する** |
| 構成の検証と監査 | **要求事項への適合性を検証する** |

[13-4 構成管理・変更管理](../13-software-development-management/13-4-構成管理-変更管理.md) で扱ったソフトウェアの構成管理と**同じ考え方**を、プロジェクトの成果物全体に適用したものである。「いま何がどの状態にあるか」を常に把握できるようにしておかなければ、変更の影響も評価できないし、完成したかどうかも判断できない。

誤答として並ぶ活動との区別を押さえる。

| 活動 | 内容 |
| --- | --- |
| **アーンド・バリュー・マネジメント** | コストとスケジュールの進捗を定量的に測る（→ [14-7 プロジェクトのコスト](14-7-プロジェクトのコスト.md)） |
| **コンフリクト・マネジメント** | 人間関係の対立を解消する（→ [14-5 プロジェクトの資源](14-5-プロジェクトの資源.md)） |
| **ポートフォリオマネジメント** | 組織全体でプロジェクトの組合せを選ぶ（→ [14-1](14-1-プロジェクトマネジメント.md)） |

**「記録・報告」「適合性の検証」という語が出てきたらコンフィギュレーション・マネジメント**である。

### 3.1 変更要求の流れ

変更は思いつきで反映してはならない。次の手順を踏む。

```mermaid
graph LR
  A["変更要求"] --> B["影響分析<br/>（スコープ・コスト・期間・品質・リスク）"]
  B --> C["変更管理委員会（CCB）<br/>による承認／却下"]
  C --> D["承認された変更の反映"]
  D --> E["ベースラインの更新と記録"]
```

**影響分析を飛ばさないこと**が要点である。「この程度なら簡単だろう」と受け入れた変更が、実は複数の成果物に波及してスケジュールを崩す、というのがプロジェクトが失敗する典型的な経路である。無制御な変更の積み重ねを**スコープクリープ**という（→ [14-4 プロジェクトのスコープ](14-4-プロジェクトのスコープ.md)）。

> **出題** PMBOKの統合変更管理: H28午前I問18

## この章のまとめ

- **プロジェクト憲章はプロジェクトを正式に認可し、プロジェクトマネージャの責任・権限を記す文書**。計画より前の立上げ段階で作られる。
- 主要文書は**憲章＝認可、スコープ記述書＝範囲、WBS＝作業の分解、マネジメント計画書＝管理の方法**。
- **統合変更管理のコンフィギュレーション・マネジメントは、変更と実施状況を記録・報告し、要求事項への適合性を検証する**。
- 変更は**影響分析 → 承認 → 反映 → 記録**の手順を踏む。飛ばすとスコープクリープを招く。
