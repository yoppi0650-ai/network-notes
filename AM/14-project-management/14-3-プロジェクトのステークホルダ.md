# 14-3 プロジェクトのステークホルダ

プロジェクトに**利害関係をもつ人や組織**を特定し、関与をマネジメントすることを扱う。

プロジェクトが技術的には正しく完成したのに失敗と評価されることがある。「依頼した部門の要求とは違っていた」「経営層の期待に応えていなかった」「現場が使ってくれなかった」といった事態である。これらはいずれも**技術の問題ではなく、関係者の期待を把握し損ねた問題**である。ステークホルダマネジメントは、この種の失敗を防ぐための領域である。

H21〜R7の午前I・午前IIでは**この小分類からの直接の出題は見当たらなかった**。ただし、コミュニケーション（→ [14-11 プロジェクトのコミュニケーション](14-11-プロジェクトのコミュニケーション.md)）やプロジェクト憲章（→ [14-2 プロジェクトの統合](14-2-プロジェクトの統合.md)）と密接に関わる。

## 1. ステークホルダとは

**ステークホルダ（利害関係者）**とは、プロジェクトの**実行や完了によって影響を受ける、または影響を与える**人や組織である。

| 分類 | 例 |
| --- | --- |
| 内部 | プロジェクトマネージャ、プロジェクトチーム、スポンサー、PMO、経営層 |
| 外部 | 発注者、利用者、取引先、協力会社、規制当局、地域社会 |

重要なのは、**「協力してくれる人」だけがステークホルダではない**ことである。プロジェクトに反対する立場の人、業務が変わることで不利益を被る部門も含まれる。むしろそうした相手こそ、早期に把握しておかないと後で大きな抵抗になる。

---

## 2. ステークホルダの特定

ステークホルダの特定は、**立上げの段階で行う**（→ [14-1 プロジェクトマネジメント](14-1-プロジェクトマネジメント.md)）。プロジェクト憲章の作成と並ぶ、最初期の活動である。

早い段階で行う理由は2つある。

- **後から見つかったステークホルダの要求は、手戻りを生む**。設計が終わってから「この部門の承認も要る」と判明すれば、要求を聞き直すところからやり直しになる。
- **関与のさせ方を計画するには、誰がいるかを先に知る必要がある**。

特定したステークホルダは一覧（ステークホルダ登録簿）にまとめ、**関心事、期待、影響力、プロジェクトへの態度**を記録する。

### 2.1 権力・関心度グリッド

ステークホルダを**権力（影響力）**と**関心度**の2軸で分類し、対応方針を決める手法がある。

| | 関心度：低 | 関心度：高 |
| --- | --- | --- |
| **権力：高** | 満足な状態を保つ | **注意して管理する**（最重要） |
| **権力：低** | 監視する（労力は最小限） | 常に情報を提供する |

**権力が高く関心も高い相手に資源を集中する**のが基本方針である。すべてのステークホルダに均等に対応するのは非効率で、かつ重要な相手への対応が手薄になる。

## 3. 関与のマネジメント

ステークホルダの現在の関与状態と、望ましい関与状態を把握し、そのギャップを埋める活動を行う。

| 関与の状態 | 内容 |
| --- | --- |
| 不認識 | プロジェクトの存在を知らない |
| 抵抗 | 知っているが変化に反対している |
| 中立 | 知っているが支持も反対もしない |
| 支持 | 支持している |
| 主導 | 積極的に成功に関与している |

**すべてのステークホルダを「主導」にする必要はない**。重要なのは、影響力の大きい相手が「抵抗」のまま放置されていないことである。

抵抗への対応は、**反対の理由を把握する**ことから始まる。単なる感情的な反発ではなく、「業務負荷が増える」「既存のやり方で問題が起きていない」といった合理的な懸念であることが多い。その懸念に具体的に応えることが、形式的な説明会を重ねるより有効である。

関与のマネジメントで中心になる手段は**コミュニケーション**であり、誰に・何を・いつ・どの手段で伝えるかを計画する（→ [14-11 プロジェクトのコミュニケーション](14-11-プロジェクトのコミュニケーション.md)）。

---

## この章のまとめ

- **ステークホルダには、協力者だけでなく反対者や影響を受ける部門も含まれる**。
- 特定は**立上げの段階で行う**。後から見つかると手戻りになる。
- **権力と関心度の2軸で分類し、権力も関心も高い相手に資源を集中する**。
- **抵抗には、反対の理由を把握して具体的に応える**ことが有効。形式的な説明の繰り返しでは解消しない。
