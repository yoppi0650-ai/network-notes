# 14-5 プロジェクトの資源

プロジェクトに必要な**人・物・設備**を確保し、活用する管理を扱う。とりわけ**人的資源**の扱いが中心になる。

資源マネジメントが難しいのは、人が機械のように加算できないからである。「遅れているから人を増やす」という対応が、かえって遅れを拡大させることはよく知られている。新しい要員への説明や引継ぎに既存メンバの時間が取られ、コミュニケーションの経路も増えるためである。本章ではこうした人的資源に固有の性質を押さえる。

H21〜R7の午前I・午前IIでは**この小分類からの直接の出題は見当たらなかった**。ただし、要員追加による期間短縮（クラッシング → [14-6 プロジェクトの時間](14-6-プロジェクトの時間.md)）やコミュニケーションパスの計算（→ [14-11 プロジェクトのコミュニケーション](14-11-プロジェクトのコミュニケーション.md)）といった形で、関連する内容は問われている。

## 1. 資源の種類

| 種類 | 例 |
| --- | --- |
| 人的資源 | 要員、スキル、工数 |
| 物的資源 | 機器、ソフトウェアライセンス、設備、材料 |

資源マネジメントの流れは、**見積り → 確保 → 育成・管理** となる。WBSから分解したアクティビティごとに必要な資源を見積り（→ [14-4 プロジェクトのスコープ](14-4-プロジェクトのスコープ.md)）、調達または社内から確保し、プロジェクト期間中に活用する。

## 2. 組織の形態

プロジェクトをどういう組織形態で動かすかによって、プロジェクトマネージャの権限が変わる。

| 形態 | 特徴 | PMの権限 |
| --- | --- | --- |
| **機能型組織** | 部門長が指揮する。メンバは所属部門の業務と兼務 | **弱い** |
| **マトリックス型組織** | 部門とプロジェクトの両方から指示を受ける | 中程度 |
| **プロジェクト型組織** | プロジェクト専任のチームを編成する | **強い** |

**マトリックス型組織では、メンバが2人の上司をもつ**ことになる。部門長とプロジェクトマネージャの指示が食い違えば、メンバは板挟みになる。この構造的な問題を避けるため、**どちらがどこまでの権限をもつかを事前に明確にしておく**必要がある。プロジェクト憲章でPMの権限を明記するのは、このためでもある（→ [14-2 プロジェクトの統合](14-2-プロジェクトの統合.md)）。

## 3. 責任分担マトリックス

**責任分担マトリックス（RAM）**は、**作業と人（または組織）を対応付けた表**である。代表的な形式が**RACIチャート**である。

| | Aさん | Bさん | Cさん |
| --- | --- | --- | --- |
| 要件定義 | **A** | R | C |
| 設計 | A | **R** | I |
| テスト | A | C | **R** |

| 記号 | 意味 |
| --- | --- |
| **R**（Responsible） | 実行責任者。実際に作業する |
| **A**（Accountable） | 説明責任者。最終的な責任を負う。**作業ごとに1人だけ** |
| **C**（Consulted） | 相談される人 |
| **I**（Informed） | 報告を受ける人 |

**Aが各行に1人だけ**というのが重要な規則である。責任者が複数いる状態は、責任者が誰もいない状態と実質的に変わらない。

なお、[14-4 プロジェクトのスコープ](14-4-プロジェクトのスコープ.md) で触れたとおり、**WBS（作業の分解）とOBS（組織の分解）を対応付けたもの**がこのマトリックスである。ワークパッケージ自体が人員の割当てを含むわけではない。

## 4. 人的資源に固有の問題

### 4.1 要員追加の限界

遅れているプロジェクトに人を追加しても、期待どおりには短縮されない。理由は3つある。

- **立ち上がりの遅れ**：新しい要員が戦力になるまでに時間がかかる。その間、説明する既存メンバの生産性が落ちる。
- **コミュニケーションの増加**：人数 $n$ に対して、関係の数は $n(n-1)/2$ で増える（→ [14-11 プロジェクトのコミュニケーション](14-11-プロジェクトのコミュニケーション.md)）。
- **分割できない作業がある**：1人で3か月かかる設計を、3人で1か月にはできない。

このため、要員追加による期間短縮（**クラッシング** → [14-6 プロジェクトの時間](14-6-プロジェクトの時間.md)）は、**コストが増えるわりに効果が限定的**になる。

### 4.2 コンフリクトマネジメント

プロジェクトでは対立が避けられない。資源の取り合い、優先順位の相違、技術的な意見の対立などが起こる。

対立そのものは悪いことではなく、**放置して表面化しないまま進むほうが危険**である。異なる意見が出ることで、より良い解決策が見つかることもある。重要なのは、**問題に焦点を当て、人格の攻撃にしないこと**である。

解決の手法には、対峙（問題解決）、協調、妥協、鎮静、強制、撤退などがあり、**対峙（根本原因を特定して解決する）が最も望ましい**とされる。

なお、コンフリクトマネジメントは統合変更管理のコンフィギュレーション・マネジメントと誤答選択肢で混同されることがある（→ [14-2 プロジェクトの統合](14-2-プロジェクトの統合.md)）。**「人間関係の対立」がコンフリクト、「成果物の構成」がコンフィギュレーション**である。

## この章のまとめ

- 組織形態によって**プロジェクトマネージャの権限が変わる**。マトリックス型では2人の上司による板挟みが起きうるので、権限の範囲を事前に明確にする。
- **責任分担マトリックス（RACI）では、A（説明責任者）は作業ごとに1人だけ**。
- **要員を追加しても期間は比例して短縮しない**。立ち上がりの遅れ、コミュニケーションの増加、分割できない作業があるため。
- **対立は放置するほうが危険**。問題に焦点を当て、人格の攻撃にしない。
