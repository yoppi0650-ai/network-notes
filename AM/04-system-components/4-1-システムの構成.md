# 4-1 システムの構成

複数のコンピュータや装置を**どう組み合わせてシステムにするか**を扱う。

ここで繰り返し現れる問いは「**壊れたときどうするか**」である。単体の部品は必ず壊れる。それを前提に、壊れても業務が止まらないよう冗長化し、壊れ方を安全な側に寄せ、そもそも壊れにくくする──こうした設計思想が信頼性設計であり、この分野の中心テーマになっている。もう一つの軸が**処理をどこに置くか**（集中／分散、クライアントサーバ／ピアツーピア、クラウド／エッジ）である。

ネットワークスペシャリスト午前IIでは問22〜25から、午前Iでは問5前後から出題される。16年で30問と出題が多く、**信頼性設計の用語**と**SOA**が頻出である。

## 1. システムの処理形態

### 1.1 クライアントサーバとピアツーピア

| 方式 | 特徴 |
| --- | --- |
| **クライアントサーバ** | **サービスの提供や管理を特定のコンピュータが行い、他のコンピュータはそのサービスを利用するという、役割分担を明確にしたシステム**。管理が容易だが、サーバに負荷とリスクが集中する |
| **ピアツーピア (P2P)** | すべてのノードが対等にサービスの提供者にも利用者にもなる |

**ピアツーピアシステムの特徴**として出題されたのは、

> **アカウントの管理やセキュリティの管理をすることが難しく、不特定多数の利用者が匿名で接続利用できるなどの隠蔽性が高い。**

中央に管理者がいないという構造が、そのまま長所と短所の両方を生む。管理サーバが要らないので安価に大規模化でき、一部が落ちても全体は止まらない。しかしその裏返しとして、**誰が何を持っているかを統制できない**。ファイル共有ソフトによる情報漏えいが社会問題になったのは、この性質による。

誤答として並ぶ記述はいずれもクライアントサーバ型の特徴である。「役割分担を明確にしたシステムを簡単に作成できる」「データアクセスの負荷が全体を監視するコンピュータに集中する」「目的のデータの存在場所が明確なので高速に検索できる」は、中央に管理者がいることを前提にしている。

### 1.2 シンクライアント

**シンクライアント**は、端末側の機能を最小限にして、アプリケーションの実行とデータの保管をサーバ側で行う方式である。

利点として出題されたのは、

> **サーバ側でアプリケーションやデータを管理するので、セキュリティが強化できる。**

**端末にデータが残らない**ので、端末の紛失・盗難による情報漏えいが起きない。この性質がシンクライアントの最大の価値である。[11-4 情報セキュリティ対策](../11-security/11-4-情報セキュリティ対策.md) で扱ったVDIによるインターネット分離も、同じ原理を応用したものである。

誤答との区別も押さえる。シンクライアントは**画面情報をネットワーク経由でやり取りするので通信量はむしろ増える**。「ネットワーク資源が減るので通信費を削減できる」は誤りである。また、データをサーバに集約するので**サーバへの投資は増える**。「サーバへの投資を削減できる」も誤りである。シンクライアントは**セキュリティと運用管理のコストを、通信とサーバのコストで買う**方式だと理解しておくとよい。

### 1.3 ミッションクリティカルシステム

**ミッションクリティカルシステム**とは、

> **障害が起きると、企業活動に重大な影響を及ぼすシステム**

である。金融機関の勘定系、交通機関の運行管理、生命に関わる医療機器などが該当する。高い可用性と信頼性が要求され、本章で扱う冗長化や信頼性設計が重点的に適用される。

「OSのように業務システムを稼働させるうえで必要不可欠なシステム」（基盤ソフトウェア）、「性能の限界に近い状態で稼働するシステム」、「先行して試験導入されるシステム」（パイロットシステム → [12-5 導入・受入れ支援](../12-system-development/12-5-導入-受け入れ支援.md)）とは異なる。

> **出題** シンクライアント: H21午前II問23 ｜ ミッションクリティカルシステム: H25午前I問20 ｜ ピアツーピア: R1午前II問23

## 2. 信頼性設計

**最頻出テーマ**である。4つの用語の定義を正確に区別することが問われる。

| 用語 | 考え方 |
| --- | --- |
| **フェールセーフ** | **障害が発生したときでも、常に安全側にシステムを制御する**。あらかじめ指定された安全な状態に固定する |
| **フェールソフト** | **障害が発生したときに、すぐに停止せず機能を縮退させて運用を継続する**（フォールバック運転） |
| **フールプルーフ** | **不特定多数の人が操作しても、誤動作が起こりにくいように設計する**。誤った使い方を未然に防ぐ |
| **フォールトトレランス** | 構成要素を**多重化**して、故障が発生してもシステム全体としては機能を保つ |

4つは**「誰の・いつの・どういう失敗」に備えるか**が違う。

- **フールプルーフは「人が間違える」ことへの備え**。故障が起きる前の段階で、人の誤操作を受け付けないようにする。
- **フェールセーフは「機械が壊れたときに危険な側へ倒れない」ための備え**。踏切の遮断機が停電時に下りるのが典型例である。
- **フェールソフトは「壊れても全部は止めない」ための備え**。性能は落ちるが業務は続く。
- **フォールトトレランスは「壊れても気づかせない」ための備え**。多重化で肩代わりする。

**フールプルーフの具体例**として出題されたものを挙げる。

> **メニュー画面上の使用権限のない機能は、実行できないようにする。**

> **システムに規定外の無効なデータが入力されたとき、誤入力であることを伝えるメッセージを表示して正しい入力を促すことによって、システムを異常終了させない設計。**

> 不特定多数の人が使用するプログラムには、より多くデータチェックの機能を組み込み、前提条件を満たさないデータが入力されたときはエラーメッセージを表示して再入力を促す。

いずれも**「人の誤りを想定して、そもそも受け付けない／正しく導く」**という共通点がある。「更新対象のデータをコピーして保存する」（バックアップ）、「取消し操作ができるようにする」（アンドゥ）、「操作内容をログとして保存する」（証跡管理）はフールプルーフではない。

### 2.1 フォールトアボイダンスとフォールトトレランス

| 用語 | 考え方 |
| --- | --- |
| **フォールトアボイダンス（故障回避）** | **故障が発生したときに対処するのではなく、品質管理などを通じてシステム構成要素の個々の品質を高めて、故障が発生しないようにする** |
| **フォールトトレランス（耐故障）** | 故障は起きるものとして、多重化で耐える |
| フォールトマスキング | 故障の影響が外部に誤りとなって出ないよう、内部で訂正する |

**「壊さない」がフォールトアボイダンス、「壊れても耐える」がフォールトトレランス**という対比で覚える。前者は部品の品質向上や予防保守で実現し、後者は冗長構成で実現する。どちらか一方では足りないので、実際のシステムは両方を組み合わせる。

誤答では4つの用語の説明が互いに入れ替えられる。典型的な誤りを挙げる。

| 誤った記述 | 正しくは |
| --- | --- |
| フェールソフトとは、あらかじめ指定された安全な状態にシステムを保つこと | **フェールセーフ** |
| フェールソフトとは、機能を縮退させることなく稼働を継続する概念 | 縮退**させて**継続するのがフェールソフト |
| フォールトマスキングとは、縮小した範囲のサービスを提供すること | **フェールソフト** |
| フェールセーフとは、故障の影響が誤りとなって外部に出ないように訂正すること | **フォールトマスキング** |
| フェールセーフとは、単純なミスを発生させないようにする設計方法 | **フールプルーフ** |
| フォールトトレランスとは、あらかじめ定められた安全状態に固定する設計方法 | **フェールセーフ** |

> **出題** フェールセーフ: H21午前I問5、H25午前I問5 ｜ 信頼性向上技術: H22午前I問5 ｜ フールプルーフ: H23午前I問9、H30午前I問16、R4午前II問24、R6午前II問24 ｜ 信頼性設計: R6午前I問5

## 3. 冗長化とクラスタリング

**クラスタリング**は、複数のコンピュータ（ノード）を結合して1つのシステムとして動作させる構成である。

ノード障害が発生したときに信頼性を向上させる機能は、

> **障害ノードを排除して代替ノードでアプリケーションを実行させるフェールオーバ機能が働く。**

| 用語 | 内容 |
| --- | --- |
| **フェールオーバ** | **障害ノードを切り離し、代替ノードに処理を引き継がせる** |
| フェールバック | 障害から復旧した元のノードに処理を戻す |
| ホットプラグ | 電源を入れたまま機器を交換する機能。クラスタの切替えとは別物 |

誤答の区別も押さえる。「代替ノードを再起動する」のでは引継ぎにならないし（代替ノードは元から動いている）、「ノード間の通信が途切れたときにフェールバック機能が働く」のも誤りである。**フェールバックは復旧後に戻す動作**であって、障害時の切替えではない。

冗長構成の運転形態も整理しておく。

| 構成 | 待機系の状態 |
| --- | --- |
| ホットスタンバイ | 常に起動して同期しており、即座に切り替わる |
| ウォームスタンバイ | 起動はしているが処理は引き継いでいない |
| コールドスタンバイ | 停止しており、障害時に起動する。安価だが切替えに時間がかかる |
| デュプレックスシステム | 主系と待機系に分け、待機系は平常時に別の処理を行う |
| デュアルシステム | 2系統で同じ処理を行い、結果を照合する。最も信頼性が高いがコストも高い |

> **出題** クラスタリングシステムのノード障害時の機能: H27午前I問5

## 4. ストレージの構成

### 4.1 接続形態

| 形態 | 接続方法 |
| --- | --- |
| **DAS** (Direct Attached Storage) | **シリアルATAなどの接続方式によって内蔵ストレージとして1対1に接続する**（→ [3-4 入出力デバイス](../03-computer-components/3-4-入出力デバイス.md)） |
| **NAS** (Network Attached Storage) | **プロトコルはNFSやCIFSを使用し、LANで接続する**。ファイル単位でアクセスする |
| **SAN** (Storage Area Network) | **磁気ディスク装置や磁気テープ装置などのストレージを、通常のLANとは別の高速な専用ネットワークで構成する**。**ファイバチャネルなどによる専用ネットワークで接続**し、ブロック単位でアクセスする |

**SANの要点は「通常のLANとは別の専用ネットワーク」**である。ストレージへのアクセスは業務通信とは比べものにならない量とタイミングのシビアさがあるため、同じLANに相乗りさせると双方が足を引っ張り合う。分離することで、ストレージ側は低遅延を確保でき、LAN側も圧迫されない。

NASとSANの違いは**アクセスの単位**にもある。NASは「ファイルをください」とサーバに頼む（ファイルシステムはNAS側にある）。SANは「このブロックをください」と直接読む（ファイルシステムはサーバ側にある）。だからSANに接続したストレージは、サーバから見ると内蔵ディスクと同じように扱える。

**FCoE（Fibre Channel over Ethernet）**は、**転送ロスを発生させないための拡張がされたイーサネットで、FCフレームを通信する**技術である。SANのためにファイバチャネルの専用配線を別に敷くのはコストがかかるので、イーサネットに相乗りさせたい。しかし通常のイーサネットは輻輳時にフレームを捨てるので、ストレージ通信には耐えられない。そこで**フレームを落とさない拡張（DCB）を施したイーサネット**の上でFCフレームを運ぶ。

ここで重要なのは、**FCoEはTCPもUDPも使わない**という点である。FCフレームをイーサネットフレームに直接載せる（レイヤ2で動く）ので、IPもその上のトランスポート層も経由しない。「オーバヘッドを小さくするためUDPを用いる」「信頼性確保のためTCPを用いる」はいずれも誤りである。また、FCフレームは2,000オクテット超になるため、**イーサネット側がジャンボフレームに対応する**必要がある。「イーサネットのパケットサイズに合わせてFCフレームサイズが調整される」のではなく、逆である。

### 4.2 RAID

**RAID**は複数の磁気ディスクを組み合わせて信頼性や性能を高める技術である。

| 方式 | 構成 |
| --- | --- |
| RAID0 | ストライピング。データを分散して書き、高速化する。冗長性はない |
| **RAID1** | ミラーリング。**同じデータを複数台のハードディスクに書き込み、冗長化する** |
| RAID3 | **ビット／バイト単位**のストライピング＋**パリティ専用ディスク** |
| **RAID4** | **ブロック単位**のストライピング＋**パリティ専用ディスク** |
| RAID5 | ブロック単位のストライピング＋**パリティを各ディスクに分散** |

**「パリティ専用の磁気ディスク装置をもち、ブロック単位のストライピングを行う」のはRAID4**である。RAID3と迷いやすいが、**RAID3はビット／バイト単位、RAID4はブロック単位**という違いで区別する。

RAID4の弱点は、書込みのたびに必ずパリティ専用ディスクへのアクセスが発生し、そこがボトルネックになることである。これを解消するためにパリティを全ディスクに分散させたのがRAID5であり、実用上はRAID5やRAID6が使われる。

### 4.3 シン・プロビジョニング

**シン・プロビジョニング**は、

> **利用者の要求に対して仮想ボリュームを提供し、物理ディスクは実際の使用量に応じて割り当てる。**

従来は「将来1 TB必要になるかもしれない」という見込みで1 TBの物理ディスクを先に確保していたため、使われない領域が大量に遊んでいた。シン・プロビジョニングでは、利用者には1 TBのボリュームに見せつつ、物理ディスクは実際に書き込まれた分だけ消費する。**必要になった時点で買い足せばよい**ので、初期投資を抑えられる。

誤答との区別も押さえる。「同じデータを複数台に書き込んで冗長化する」はRAID1（ミラーリング）、「1台のディスクを領域分割する」はパーティショニング、「ファイバチャネルでストレージをネットワーク化する」はSANである。

> **出題** SAN: H23午前II問7、H25午前II問23 ｜ FCoE: H25午前II問7 ｜ RAID: H27午前II問22 ｜ シン・プロビジョニング: H24午前II問22

## 5. 分散処理とクラウド

### 5.1 グリッドコンピューティング

**グリッドコンピューティング**は、

> **PCから大型コンピュータまで、ネットワーク上にある複数のプロセッサに処理を分散して、大規模な一つの処理を行う方式**

である。遊休資源を寄せ集めて1台のスーパーコンピュータのように使う発想で、科学技術計算で使われてきた。

誤答に並ぶ他の分散方式との区別を押さえる。

| 記述 | 実際は何か |
| --- | --- |
| OSを実行するプロセッサ、アプリケーションを実行するプロセッサというように役割が決まっている | 非対称型マルチプロセッサ（ASMP） |
| カーネルプロセスとユーザプロセスを区別せず、同等な役割の複数プロセッサに分散する | 対称型マルチプロセッサ（**SMP**） |
| プロセッサ上でスレッドレベルの並列化を実現し、利用効率を高める | マルチスレッディング（→ [3-1 プロセッサ](../03-computer-components/3-1-プロセッサ.md)） |

### 5.2 スケールアップとスケールアウト

処理能力を調整する方向に2つある。

| 用語 | 内容 |
| --- | --- |
| スケールアップ | サーバ1台の**能力（CPU・メモリ）を増やす** |
| スケールダウン | サーバ1台の能力を減らす |
| スケールアウト | サーバの**台数を増やす** |
| **スケールイン** | **想定されるシステムの処理量に対してサーバの台数が過剰なとき、サーバの台数を減らすこと** |

**「アップ／ダウン」が能力の増減、「アウト／イン」が台数の増減**である。クラウドでは需要に応じて台数を自動で増減させる（オートスケール）ことで、コストと性能のバランスを取る。

### 5.3 クラウドのサービスモデル

| モデル | 利用者が使えるもの |
| --- | --- |
| IaaS | **演算機能、ストレージ、ネットワークなどをクラウドに配置して使用できる** |
| PaaS | アプリケーションの実行基盤（ミドルウェアまで） |
| SaaS | **クラウドサービス事業者が提供するアプリケーションプログラムを使用できる** |
| **FaaS** | **プログラムの実行環境であるサーバの管理を意識する必要がなく、その実行環境を使用できる** |
| DaaS | **仮想化したデスクトップ環境を遠隔地の端末から使用できる** |

**FaaS（Function as a Service）**は、「サーバレス」と呼ばれる形態である。利用者は関数（処理の単位）だけを登録しておき、イベントが起きたときだけ実行される。サーバの台数も起動状態も意識しなくてよく、実行した分だけ課金される。**管理の対象が「サーバ」から「関数」に移った**という点が、他のモデルとの本質的な違いである。

### 5.4 エッジコンピューティングとエッジAI

**エッジコンピューティング**は、

> **演算処理のリソースを端末の近傍に置くことによって、アプリケーション処理の低遅延化や通信トラフィックの最適化を行う。**

クラウドに全データを送って処理する方式では、**往復の遅延**と**通信量**が問題になる。工場の設備制御や自動運転のように「数ミリ秒で判断したい」用途では、遠くのクラウドを往復していては間に合わない。また無数のIoT機器が生データを送り続ければ回線が飽和する。そこで**端末の近くで処理を済ませ、必要な結果だけをクラウドへ送る**。

誤答との区別も押さえる。「データの特徴を学習して事象の認識や分類を行う」は機械学習、「ネットワークを介して複数のコンピュータを結んで処理能力の高いシステムを作る」はグリッドコンピューティング、「周りの環境から微小なエネルギーを収穫して電力に変換する」は**エネルギーハーベスティング**（→ [6-1 ハードウェア](../06-hardware/6-1-ハードウェア.md)）である。

**エッジAI**はこの考え方をAIに適用したもので、**クラウドで学習し、エッジデバイスで推論する**構成を採る。学習は大量のデータと計算資源を要するのでクラウドで行い、推論は軽いのでエッジで行う、という役割分担である。

エッジデバイスで行われる**推論処理**とは、

> **学習したモデルに従い、実際にデータの識別などを行うプロセス**

である。誤答に並ぶ「試行錯誤を行い行動に報酬を与える」（強化学習）、「正解のラベルを付けたデータでモデルを作成する」（教師あり学習）、「正解のラベルを付けないデータでモデルを作成する」（教師なし学習）は、いずれも**学習**のプロセスであって推論ではない（→ [1-3 情報に関する理論](../01-basic-theory/1-3-情報に関する理論.md)）。

> **出題** グリッドコンピューティング: H23午前II問23 ｜ スケールイン: R5午前I問5 ｜ FaaS: R5午前II問23 ｜ エッジコンピューティング: H29午前I問28、R6午前I問28 ｜ エッジAI: R7午前I問27

## 6. SOA

**SOA（Service Oriented Architecture、サービス指向アーキテクチャ）**は**5回出題されている頻出テーマ**である。

> **ビジネスプロセスの構成要素とそれを支援するIT基盤を、ソフトウェア部品であるサービスとして提供するシステムアーキテクチャ**

> **業務機能を提供するサービスを組み合わせることによって、システムを構築する考え方**

> **利用者の視点から業務システムの機能を幾つかの独立した部品に分けることによって、業務プロセスとの対応付けや他ソフトウェアとの連携を容易にする手法**

3つとも同じことを言っている。要点は**「業務機能の単位でサービスに分け、それを組み合わせてシステムを作る」**ことである。

なぜこの考え方が生まれたか。業務の変化に合わせてシステムを作り変えるのが遅く、高くつくからである。システムを技術的な都合で分割すると、業務が変わったときにどこを直せばよいかわからない。**業務機能と1対1に対応する単位で分けておけば、「受注処理が変わった」という業務の変化が「受注サービスの差し替え」というシステムの変更に直結する**。

### 6.1 サービス設計の注意点

SOAでサービスを設計する際の注意点として出題されたのは、

> **業務の変化に対応しやすくするために、サービス間の関係は疎結合にする。**

これもSOAの目的から導ける。あるサービスを変更したときに他のサービスまで直さなければならないなら、変化に強いという利点が失われる。サービス同士の依存を最小限にし、インタフェースだけで結ぶ（疎結合）ことが前提条件になる。

関連する設計上の指針も押さえておく。

- **可用性を高めるため、サービスのインタフェースはステートレスにする**。状態を持たなければ、どのサーバに割り振っても同じ結果になり、多重化や負荷分散が容易になる。
- **業務からの独立性を確保するため、サービスの命名は役割を表すものにする**。技術的な実装名ではなく業務上の役割で名付ける。

### 6.2 紛らわしい概念との区別

SOAの設問では、他の経営・システム用語が誤答に並ぶ。

| 記述 | 実際は何か |
| --- | --- |
| 既存の組織やビジネスルールを抜本的に見直し、業務フロー・管理機構・情報システムを再構築する手法 | **BPR**（→ [17-2 業務プロセス](../17-system-strategy/17-2-業務プロセス.md)） |
| 経営資源を有効活用するため、基幹業務を部門ごとではなく統合的に管理する業務システム | **ERP**（→ [19-4 経営管理システム](../19-business-strategy-management/19-4-経営管理システム.md)） |
| 発注者とITアウトソーシングサービス提供者の間で、サービスの品質について合意した文書 | **SLA**（→ [15-1 サービスマネジメント](../15-service-management/15-1-サービスマネジメント.md)） |
| 業務プロセスの問題点を洗い出し、PDCAを適用して継続的改善を図る手法 | **BPM**（→ [17-2](../17-system-strategy/17-2-業務プロセス.md)） |
| Webサービスを利用するためのインタフェースやプロトコルを規定したもの | SOAP / WSDL（→ [10-5 ネットワーク応用](../10-network/10-5-ネットワーク応用.md)） |
| XMLを利用してインターネット上のWebサービスを検索できる仕組み | UDDI |
| ソフトウェアパッケージの機能性がニーズにどれだけ適合しているかを分析する手法 | フィット＆ギャップ分析 |

> **出題** SOA: H22午前I問24、H22午前II問25、H26午前I問24、H27午前II問25、H28午前II問25、R6午前I問23

## 7. 障害分析の手法

**FTA（Fault Tree Analysis、故障の木解析）**は、信頼性工学の視点で行うシステム設計において、発生し得る障害の原因を分析する手法である。

> **障害と、その中間的な原因から基本的な原因までの全てを列挙し、それらをゲート（論理を表す図記号）で関連付けた樹形図で表す。**

「システムが停止する」という**好ましくない事象（頂上事象）を出発点に、その原因を下へ下へと展開していく**。ANDゲート（すべての原因が揃ったときに起きる）とORゲート（どれか1つで起きる）で結ぶので、どの組合せが致命的かが論理的に見える。**結果から原因へ遡るトップダウンの分析**である。

誤答として並ぶ他の分析手法と区別する。

| 手法 | 方向と内容 |
| --- | --- |
| **FTA** | **トップダウン**。障害から原因へ樹形図で展開する |
| **FMEA** | **ボトムアップ**。構成品目の故障モードに着目して推定原因を列挙し、システムへの影響を評価して**定性的に分析する** |
| なぜなぜ分析 | 障害データから「なぜ」を繰り返して根本原因を明らかにする |
| ODC分析 | 互いに重ならないよう定義した**ODC属性**で障害を分類し、どこに集中しているかを調べる |

**FTAは結果から原因へ、FMEAは原因（部品の故障）から結果へ**という向きの違いが決め手になる。

> **出題** FTA: R3午前II問24

## この章のまとめ

- **ピアツーピアは中央管理者がいないため管理・統制が難しい**。シンクライアントは**端末にデータが残らないのでセキュリティが強化される**が、通信量とサーバ投資は増える。
- 信頼性設計の4語は備える対象で区別する。**フールプルーフ＝人の誤操作、フェールセーフ＝安全側に固定、フェールソフト＝縮退して継続、フォールトトレランス＝多重化で耐える**。**フォールトアボイダンスは「そもそも壊さない」**。
- クラスタリングの障害時は**フェールオーバ（代替ノードへ切替え）**。フェールバックは復旧後に戻す動作。
- ストレージは **DAS＝1対1直結、NAS＝LAN＋ファイル単位、SAN＝専用ネットワーク＋ブロック単位**。**FCoEはロスレス拡張したイーサネット上でFCフレームを運び、TCP/UDPは使わない**。
- **RAID4はブロック単位のストライピング＋パリティ専用ディスク**（RAID3はビット／バイト単位）。**シン・プロビジョニングは使った分だけ物理割当て**。
- **スケールアップ／ダウンは能力、スケールアウト／インは台数**。**FaaSはサーバ管理を意識せず実行環境を使える**。**エッジコンピューティングは端末近傍で処理して低遅延化と通信最適化**。
- **SOAは業務機能の単位でサービスに分け、疎結合に組み合わせる**。BPR・ERP・SLA・BPMとは別物。
- **FTAはトップダウン（障害→原因の樹形図）、FMEAはボトムアップ（部品の故障モード→影響）**。
