# 9-2 データベース設計

データをどういう表に分けて持つかを決める工程を扱う。**正規化**、**キーと制約**、**インデックス**が主な題材である。

設計の目的は一貫している。**同じ事実を1か所にだけ持つ**ことである。同じ事実が複数の場所にあれば、片方だけ更新されて食い違う。正規化はこの重複を機械的に取り除く手順であり、制約は取り除ききれない関係を宣言して守らせる仕組みである。

午前Iの問9・問10前後から出題される。16年で9問と、分野9のなかで最も出題が多い。

## 1. 関数従属と候補キー

### 1.1 関数従属

属性 $X$ の値が決まれば属性 $Y$ の値が一意に決まるとき、「$Y$ は $X$ に**関数従属**する」といい、$X \to Y$ と書く。

たとえば「社員番号 → 氏名」は成り立つ（社員番号が決まれば氏名が決まる）が、「氏名 → 社員番号」は成り立たない（同姓同名がありうる）。

### 1.2 候補キー

**候補キー**とは、**その値が決まれば行が一意に定まり、かつ余分な属性を含まない**属性の組である。言い換えれば、**すべての属性がそれに関数従属する最小の組**になる。

> 関係 $R(A, B, C, D, E, F)$ において、関数従属 $A \to B$、$C \to D$、$C \to E$、$\{A, C\} \to F$ が成立するとき、関係 $R$ の候補キーはどれか。

**候補となる組から、すべての属性を決定できるかを確かめる**手順で解く。

**$\{A, C\}$ を試す。**

| 決まるもの | 根拠 |
| --- | --- |
| $A$、$C$ | 自分自身 |
| $B$ | $A \to B$ |
| $D$、$E$ | $C \to D$、$C \to E$ |
| $F$ | $\{A, C\} \to F$ |

**全6属性が決まる**ので、$\{A, C\}$ は行を一意に定める。

次に**余分な属性を含まないか**を確かめる。

- $A$ だけでは：$B$ しか決まらない（$D$、$E$、$F$ が決まらない）→ 不十分
- $C$ だけでは：$D$、$E$ しか決まらない → 不十分

どちらか一方を取り除くと決定できなくなるので、$\{A, C\}$ は**最小**である。したがって候補キーは **$\{A, C\}$** となる。

$\{A, C, E\}$ も行を一意に定めるが、$E$ は余分なので候補キーではない（**スーパーキー**とは呼ばれる）。

**解き方の定石は「候補の組から出発して、決まる属性を芋づる式に広げていく」**ことである。全属性に到達できれば一意性があり、どの属性を抜いても到達できなくなれば最小性がある。

> **出題** 関数従属と候補キー: H26午前I問9

## 2. 正規化

**正規化**は、データの重複と更新時の不整合を取り除くために、表を分解していく手順である。

### 2.1 各正規形の条件

| 正規形 | 条件 |
| --- | --- |
| **第1正規形** | **繰返し属性が存在しない**（1つのセルに複数の値が入っていない） |
| **第2正規形** | **どの非キー属性も、主キーの真部分集合に対して関数従属しない**（部分関数従属がない） |
| **第3正規形** | **どの非キー属性も、主キーに推移的に関数従属しない** |

対応を問う設問では、**条件文のキーワード**で判別する。

- 「**繰返し属性**」→ **第1正規形**
- 「**主キーの真部分集合**」（＝主キーの一部）→ **第2正規形**
- 「**推移的**」→ **第3正規形**

### 2.2 第2正規形から第3正規形への変換

> **関係を第2正規形から第3正規形に変換する手順**はどれか。

答えは、

> **候補キー以外の属性間に関数従属性がある場合、その関係を分解する。**

第3正規形で取り除くのは**推移的関数従属**である。$\text{主キー} \to X \to Y$ という連鎖があると、$Y$ は主キーに**間接的に**従属していることになる。これは「候補キー以外の属性 $X$ から、別の非キー属性 $Y$ への関数従属がある」ことと同じである。

具体例で確認する。

| 社員番号（主キー） | 氏名 | 部門コード | 部門名 |
| --- | --- | --- | --- |
| 001 | 山田 | D01 | 営業部 |
| 002 | 鈴木 | D01 | 営業部 |
| 003 | 佐藤 | D02 | 開発部 |

ここには $\text{社員番号} \to \text{部門コード} \to \text{部門名}$ という推移的従属がある。その結果、**「D01 は営業部」という事実が社員の数だけ重複して記録される**。営業部が改称されたら全行を更新しなければならず、1行でも漏れれば矛盾する。

これを分解する。

| 社員番号 | 氏名 | 部門コード |
| --- | --- | --- |
| 001 | 山田 | D01 |
| 002 | 鈴木 | D01 |
| 003 | 佐藤 | D02 |

| 部門コード | 部門名 |
| --- | --- |
| D01 | 営業部 |
| D02 | 開発部 |

**「D01 は営業部」という事実が1か所にだけ存在する**状態になった。改称は1行の更新で済み、矛盾が原理的に起こらない。これが正規化の目的である。

誤答として並ぶ記述も確認する。

| 記述 | どの変換か |
| --- | --- |
| 候補キー以外の属性から、候補キーの一部の属性に対して関数従属性がある場合に分解する | ボイス・コッド正規形に関わる記述 |
| **候補キーの一部の属性から、候補キー以外の属性への関数従属性がある場合に分解する** | **第1正規形 → 第2正規形**（部分関数従属の除去） |
| **一つの属性に複数の値が入っている場合、単一の値になるように分解する** | **非正規形 → 第1正規形** |

**「どこからどこへの従属を取り除くか」**で区別する。第2正規形は「主キーの一部から非キー属性へ」、第3正規形は「非キー属性から非キー属性へ」である。

### 2.3 正規化のトレードオフ

正規化を進めると更新時の不整合はなくなるが、**データを取り出すときに表を結合する必要が増える**ため、検索性能は落ちる。そのため、性能を優先して意図的に正規化を崩す**非正規化**を行うこともある。これは「不整合のリスクを運用で管理する代わりに性能を取る」という判断であり、安易に行うべきものではない。

> **出題** 第3正規形への変換: H25午前I問10、R7午前I問9 ｜ 正規形の特徴: R4午前I問8

## 3. キーと参照制約

### 3.1 キーの種類

| キー | 意味 |
| --- | --- |
| 候補キー | 行を一意に識別できる最小の属性の組 |
| **主キー** | 候補キーのうち、代表として選んだもの。**NULLは許されない** |
| **外部キー** | 他の表の主キー（または候補キー）を参照する属性 |

### 3.2 参照制約

**参照制約（参照整合性制約）**は、**外部キーの値が、参照先の表に必ず存在すること**を保証する制約である。

> 次の表定義において、「在庫」表の製品番号に定義された**参照制約によって拒否される可能性のある操作**はどれか。
>
> 在庫（<u>在庫管理番号</u>、*製品番号*、在庫量）
> 製品（<u>製品番号</u>、製品名、型、単価）

答えは **「在庫」表への行追加**である。

参照制約が守るのは、**「在庫」表の製品番号が、必ず「製品」表に存在すること**である。どの操作がこれを壊しうるかを考える。

| 操作 | 制約に違反しうるか |
| --- | --- |
| **「在庫」表への行追加** | **存在しない製品番号を入れれば違反する** → 拒否されうる |
| 「在庫」表の行削除 | 参照する側が減るだけなので違反しない |
| 「在庫」表の表削除 | 同上 |
| 「製品」表への行追加 | 参照される側が増えるだけなので違反しない |

**参照する側（子）の追加・更新**と、**参照される側（親）の削除・更新**が、制約に違反しうる操作である。この問題では「製品」表の**削除**が選択肢になかったため、答えは「在庫」表への行追加になる。

### 3.3 参照動作（ON DELETE）

参照される側の行が削除されたとき、参照する側をどうするかを指定できる。

| 指定 | 動作 |
| --- | --- |
| **CASCADE** | **参照している行も一緒に削除する** |
| RESTRICT / NO ACTION | **削除を拒否する**（参照している行があれば削除させない） |
| SET NULL | 参照している行の外部キーをNULLにする |
| SET DEFAULT | 参照している行の外部キーを既定値にする |

> 「商品」表の行を削除したとき、**削除した行の商品コードと同じ値の商品コードをもつ「受注」表の行を自動的に削除する**SQL文として、`ON DELETE a` の `a` に入れる字句はどれか。

答えは **CASCADE** である。「連鎖する（cascade）」という語のとおり、削除が参照元にも波及する。

**CASCADEは便利だが危険でもある**。1行の削除が連鎖して大量の行を消すことがあるためである。参照の階層が深ければ、どこまで波及するか把握しにくい。業務データでは RESTRICT にして**削除を拒否し、明示的に順序立てて消させる**ほうが安全な場合が多い。

> **出題** 参照制約: H22午前I問11 ｜ ON DELETE CASCADE: R7午前I問10

## 4. E-R図とデータモデル

**E-R図（実体関連図）**は、実体（エンティティ）と関連（リレーションシップ）でデータ構造を表す。

### 4.1 多重度

関連の両端に、**何個と対応するか（多重度、カーディナリティ）**を書く。UMLの記法では次のように表す。

| 記法 | 意味 |
| --- | --- |
| `1` | ちょうど1 |
| `0..1` | 0または1 |
| `0..*` | 0以上（何個でもよい） |
| `1..*` | **1以上**（少なくとも1つは必要） |

> UMLを用いて表したデータモデルの a、b に入れる多重度はどれか。
>
> 〔条件〕
> (1) 部門には**1人以上**の社員が所属する。
> (2) 社員はいずれか一つの部門に所属する。
> (3) 社員が部門に所属した履歴を「所属履歴」として記録する。
>
> `部門 1 ─ a 所属履歴 b ─ 1 社員`

**条件を多重度に翻訳する**。

- **a（部門から見た所属履歴の数）**：条件(1)より、部門には1人以上の社員が所属する。所属履歴はその所属の記録なので、**1つの部門に対して1件以上**の履歴が存在する。したがって **`1..*`**。
- **b（社員から見た所属履歴の数）**：条件(2)より、社員はいずれか一つの部門に所属する。つまり**1人の社員に対して少なくとも1件**の所属履歴がある。異動すれば複数件になる。したがって **`1..*`**。

答えは **a: `1..*`、b: `1..*`** である。

**「0以上」か「1以上」かの判断が要点**で、条件文の「1人以上」「いずれか一つの」という表現が**0を許さない**ことを示している。「所属していない社員もありうる」なら `0..*` になる。

### 4.2 自己参照と階層構造

同じ実体どうしに関連を持たせることを**自己参照**という。「組織」が「親組織」と「子組織」の関係を持つ、といった構造である。

> E-R図の解釈として適切なものはどれか。ここで、`**` は多対多の関連を表し、自己参照は除くものとする。

**多対多の自己参照が意味するもの**を考える。

- **1つの組織が複数の親組織をもちうる**（多対多なので）。したがって**ある組織の親組織の数が、子組織の数より多い可能性がある**。
- 多対多であれば、組織は単純な木構造ではなく**ネットワーク構造**になる。「ネットワーク構造になっていない」は誤りである。
- 階層の深さは図からは決まらない。「2段階の階層構造である」とは言えない。
- 「全ての組織は必ず子組織をもつ」も、多重度が0を許すなら成り立たない（末端の組織には子がない）。

**多対多の自己参照は、木ではなく網（ネットワーク）を表す**という点が、この種の設問の核心である。

> **出題** E-R図: H25午前I問16 ｜ UMLによるデータモデルと多重度: R5午前I問9

## 5. インデックス

**インデックス（索引）**は、検索を高速化するためのデータ構造である。本の索引と同じで、全ページを読まずに目的の項目にたどり着ける。

### 5.1 B+木インデックス

関係データベースのインデックスには**B+木**が広く使われる。平衡木の一種で、**どの葉に到達するにも同じ深さをたどる**ように保たれる（→ [2-1 データ構造](../02-algorithms-and-programming/2-1-データ構造.md)）。

> B+木インデックスが定義されている候補キーを利用して1件のデータを検索するとき、**データ総件数 $X$ に対するノードへのアクセス回数のオーダ**を表す式はどれか。

答えは **$\log X$** である。

木の各ノードが複数の子を持つため、1段下るごとに探索範囲が大きく絞られる。データが $X$ 件あっても、**木の深さは $\log X$ のオーダ**にしかならない。これはデータが100倍になっても深さは数段しか増えないということで、大規模なデータでも検索時間がほとんど変わらない。

$\sqrt{X}$、$X$（線形探索相当）、$X!$ はいずれも誤りである。**$\log$ が出てくるのは「毎回範囲が一定割合に絞られる」探索の特徴**であり、2分探索や2分木と共通する（→ [2-2 アルゴリズム](../02-algorithms-and-programming/2-2-アルゴリズム.md)）。

### 5.2 インデックスの設計

インデックスは万能ではない。

| 利点 | 欠点 |
| --- | --- |
| 検索が速くなる | **更新のたびにインデックスも更新するので、追加・更新・削除が遅くなる** |
| 整列済みの取り出しが速い | 記憶領域を消費する |

したがって、**検索の多い列には付け、更新の多い列には慎重になる**。また、取りうる値の種類が少ない列（性別など）にインデックスを付けても、絞り込みの効果が小さいため効果が薄い。

これは [9-1 データベース方式](9-1-データベース方式.md) の3層スキーマでいう**内部スキーマの設計**にあたり、DBAの領分である。インデックスを追加してもアプリケーションを書き換えなくてよいのは、物理データ独立性が保たれているためである。

> **出題** B+木インデックス: H28午前I問9

## この章のまとめ

- **候補キーは「すべての属性を決定でき、かつ最小」の属性の組**。候補から出発して決まる属性を芋づる式に広げ、全属性に到達するか・どれを抜いても到達できなくなるかを確かめる。
- 正規形は条件文のキーワードで判別する。**「繰返し属性」＝第1、「主キーの真部分集合」＝第2、「推移的」＝第3**。
- **第3正規形への変換は「候補キー以外の属性間の関数従属を分解する」**。目的は**同じ事実を1か所にだけ持つ**こと。
- 参照制約に違反しうるのは**参照する側の追加・更新**と**参照される側の削除・更新**。**ON DELETE CASCADE は参照元も連鎖削除する**。
- 多重度は条件文の「1以上か0以上か」で決まる。**多対多の自己参照はネットワーク構造**を表す。
- **B+木インデックスのアクセス回数のオーダは $\log X$**。検索は速くなるが更新は遅くなる。
