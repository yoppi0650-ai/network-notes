# 17-4 システム活用促進及び評価

導入したシステムを**実際に使ってもらい、効果を評価し、不要になれば廃棄する**までを扱う。

システムは導入しただけでは価値を生まない。使われて初めて効果が出る。しかし現場では「使い方が分からない」「従来のやり方のほうが早い」という理由で定着しないことがある。**導入と活用は別の課題**であり、後者には別の働きかけが要る。本章はその領域である。

H21〜R7の午前I・午前IIでは**この小分類からの直接の出題は見当たらなかった**。ただし、IT投資の評価（→ [17-1 情報システム戦略](17-1-情報システム戦略.md)）、利用者教育（→ [12-5 導入・受入れ支援](../12-system-development/12-5-導入-受け入れ支援.md)）、データ活用（→ [22-2 業務分析・データ利活用](../22-corporate-activities/22-2-業務分析-データ利活用.md)）といった形で、関連する内容は問われている。

## 1. 情報リテラシとデジタルリテラシ

| 用語 | 意味 |
| --- | --- |
| **情報リテラシ** | 情報を収集・評価・活用する能力 |
| **デジタルリテラシ** | デジタル技術を理解し、業務に活かす能力 |
| **データリテラシ** | データを読み解き、意思決定に使う能力 |
| **デジタルディバイド** | 情報技術を使える者と使えない者の間に生じる格差 |

**デジタルディバイドが問題になるのは、システムを導入すること自体が格差を生みうる**からである。オンライン手続のみに切り替えれば、利用できない人は排除される。[7-1 ユーザインタフェース](../07-user-interface/7-1-ユーザインタフェース.md) のアクセシビリティは、この問題への技術面からの対応にあたる。

## 2. 普及啓発と定着化

システムを定着させるための働きかけには、いくつかの型がある。

| 施策 | 内容 |
| --- | --- |
| 利用者教育・研修 | 操作方法と業務手順を教える（→ [12-5 導入・受入れ支援](../12-system-development/12-5-導入-受け入れ支援.md)） |
| マニュアル・ヘルプの整備 | 参照できる形で情報を残す（→ [7-1 ユーザインタフェース](../07-user-interface/7-1-ユーザインタフェース.md)） |
| サービスデスクの設置 | 疑問や不具合にすぐ答える（→ [15-4 サービスの運用](../15-service-management/15-4-サービスの運用.md)） |
| **推進体制の整備** | 部門ごとに推進担当者を置き、現場の声を吸い上げる |
| 利用状況のモニタリング | 使われていない機能・部門を把握する |

**定着しない理由は「使い方が分からない」だけとは限らない**。「入力の手間が増えるのに自分には利点がない」という場合、研修をいくら重ねても使われない。この場合に必要なのは教育ではなく、**業務設計の見直しか、利点の可視化**である。

利用状況のモニタリングが重要なのは、**使われていないという事実から、その理由を探る出発点が得られる**からである。全社で使われていないなら設計の問題、特定部門だけなら運用や教育の問題、という切り分けができる。

## 3. 効果の評価

導入後に、**狙った効果が出ているか**を評価する。

| 観点 | 例 |
| --- | --- |
| 定量的効果 | コスト削減額、処理時間の短縮、エラー件数の減少 |
| 定性的効果 | 顧客満足度の向上、意思決定の迅速化、従業員の負担軽減 |

評価手法（ROI、NPV、PBP、バランススコアカード）は [17-1 情報システム戦略](17-1-情報システム戦略.md) で扱う。

### 3.1 事前評価と事後評価

| 時点 | 目的 |
| --- | --- |
| 事前評価 | 投資するかどうかを判断する |
| 中間評価 | 計画どおり進んでいるか、継続するかを判断する |
| **事後評価** | **狙った効果が出たかを確認し、次の投資判断に活かす** |

**事後評価が省略されがちだが、これを行わないと組織に学習が蓄積しない**。見積りが甘かったのか、効果の想定が楽観的だったのか、実行に問題があったのかを振り返らなければ、次も同じ失敗を繰り返す。

これは [13-1 開発プロセス・手法](../13-software-development-management/13-1-開発プロセス-手法.md) のCMMIが、レベル4（定量的に管理された）をレベル5（最適化している）の前提としているのと同じ構造である。**測って記録しなければ改善はできない**。

## 4. システムの廃棄

システムには寿命がある。使われなくなったシステムを放置すると、次の問題が生じる。

| 問題 | 内容 |
| --- | --- |
| 保守コスト | 使われていなくても、稼働していれば費用がかかる |
| **セキュリティリスク** | **保守されないシステムは脆弱性が放置される**（→ [11-4 情報セキュリティ対策](../11-security/11-4-情報セキュリティ対策.md)） |
| 技術的負債 | 古い技術に依存した部分が、他のシステムの刷新を妨げる |

廃棄にあたっては、**データの移行・保管と確実な消去**が重要になる（→ [12-6 保守・廃棄](../12-system-development/12-6-保守-廃棄.md)）。法定保存期間のあるデータは残し、不要なデータは復元できない形で消去する。

**「作るときは熱心だが、やめるときの計画がない」**のは情報システムによくある問題である。全体最適化計画（→ [17-1 情報システム戦略](17-1-情報システム戦略.md)）では、新規投資だけでなく、既存システムの統廃合も対象に含める必要がある。

---

## この章のまとめ

- **導入と活用は別の課題**。使われなければ効果は出ない。**デジタルディバイドは、システム導入そのものが生みうる格差**である。
- **定着しない理由が「分からない」とは限らない**。利点が見えなければ、教育を重ねても使われない。利用状況のモニタリングが原因の切り分けに役立つ。
- **事後評価を行わないと組織に学習が蓄積しない**。見積りや効果想定の精度は、振り返りによってしか上がらない。
- 使われなくなったシステムの放置は、**コストだけでなくセキュリティリスクと技術的負債**を生む。廃棄の計画も全体最適化の一部である。
