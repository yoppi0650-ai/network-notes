# 17-2 業務プロセス

**業務のやり方そのものを可視化し、改善する**領域を扱う。

[17-1 情報システム戦略](17-1-情報システム戦略.md) で述べたとおり、EAは「業務とシステムを同時に改善する」ものだった。本章はその**業務の側**に焦点を当てる。システムを新しくしても、業務の手順が古いままなら効果は出ない。むしろ**非効率な業務をそのままシステム化すれば、非効率が固定化される**。だから業務プロセスの見直しが先に来る。

午前Iの問23・問25前後から出題される。16年で7問。

## 1. 業務モデリング

### 1.1 業務モデルを定義する目的

> 情報戦略における全体最適化計画策定の段階で、**業務モデルを定義する目的**はどれか。

答えは、

> **企業の全体業務と使用される情報の関連を整理し、情報システムのあるべき姿を明確化すること。**

**この段階では、まだ個別システムの話をしていない**という点が重要である。誤答はいずれも、より後の工程の目的になっている。

| 記述 | いつの工程か |
| --- | --- |
| **全体業務と情報の関連を整理し、情報システムのあるべき姿を明確化する** | **全体最適化計画（本工程）** |
| システム化の範囲や開発規模を把握し、期間・工数・費用を見積もる | システム化計画（→ [18-1 システム化計画](../18-system-planning/18-1-システム化計画.md)） |
| ハードウェア、ソフトウェア、ネットワークなどの構成要素を洗い出す | システム方式設計（→ [12-2 設計](../12-system-development/12-2-設計.md)） |
| ユーザマニュアルや運用マニュアルを作成するために業務手順を確認する | 導入・受入れ支援（→ [12-5 導入・受入れ支援](../12-system-development/12-5-導入-受け入れ支援.md)） |

### 1.2 現物モデルと論理モデル

> **業務のあるべき姿を表す論理モデル**を説明したものはどれか。

答えは、

> **経営目標の達成に必須な業務機能を定義し、体系化したもの。**

| モデル | 表すもの |
| --- | --- |
| **現物モデル（物理モデル）** | **現状**の業務機能を分析し、体系化したもの |
| **論理モデル** | **経営目標の達成に必須な業務機能**を定義し、体系化したもの（あるべき姿） |

**論理モデルは「現状を整理したもの」ではなく「目標から導いたもの」**である。現状の業務を分析して整理しただけでは、現状の非効率もそのまま残る。経営目標から出発して「本来どういう機能が必要か」を考えるからこそ、あるべき姿になる。

誤答として並ぶ「現状の業務機能を分析し体系化したもの」は現物モデル、「現状の業務機能と情報システムの処理を分析して相互の関係を明確化したもの」は現状分析、「本来あるべき業務機能と現状を比較して差異を分析・評価したもの」は**ギャップ分析**である。

[17-1](17-1-情報システム戦略.md) のAs-Is／To-Beと対応づけると、**現物モデルがAs-Is、論理モデルがTo-Be、両者の比較がギャップ分析**という関係になる。

> **出題** 業務モデルの定義目的: H23午前I問24 ｜ 論理モデル: H25午前I問24

## 2. UMLによる業務プロセスの可視化

> 業務プロセスを可視化する手法として**UMLを採用した場合の活用シーン**はどれか。

答えは、

> **複数の観点でプロセスを表現するために、目的に応じたモデル図法を使用し、オブジェクトモデリングのために標準化された記述ルールで表現する。**

**UMLの特徴は「複数の図法がそろっていて、記述ルールが標準化されている」**ことである。1つの図ですべてを表そうとせず、目的ごとに図を使い分ける。

誤答は、いずれも**他の手法**の説明である。

| 記述 | 手法 |
| --- | --- |
| エンティティとその属性、エンティティ間の関連で捉え、データ中心アプローチで図示する | **E-R図**（→ [9-2 データベース設計](../09-database/9-2-データベース設計.md)） |
| データの流れによってプロセスを表現し、データの流れを矢印でつないで表現する | **DFD**（→ [12-1 システム・ソフトウェア要件定義](../12-system-development/12-1-システム-ソフトウェア-要件定義.md)） |
| 一つの要件に対して発生する事象を条件分岐の形式で記述する | **デシジョンツリー／決定表** |

### 2.1 業務フローにはアクティビティ図

> UMLの図のうち、業務要件定義において、**業務フローを記述する際に使用する、処理の分岐や並行処理、処理の同期などを表現できる図**はどれか。

答えは **アクティビティ図**である。

| UML図 | 表現するもの |
| --- | --- |
| **アクティビティ図** | **処理の流れ。分岐、並行処理、同期** |
| クラス図 | 静的な構造（クラスと関連） |
| 状態マシン図 | 状態の遷移 |
| ユースケース図 | システムとアクタの相互作用 |

**「分岐」「並行処理」「同期」という語が出てきたらアクティビティ図**である。業務フローには「条件によって処理が分かれる」「複数の部署が同時に作業する」「両方が終わってから次へ進む」といった構造が必ず現れるので、これらを表現できる図が要る。

**スイムレーン**（縦または横のレーンで担当者・部署を区切る）を使えば、「どの処理を誰がやるか」も同時に表せる。業務フローの可視化でアクティビティ図が選ばれるのは、この表現力による。

他のUML図の詳細は [12-1 システム・ソフトウェア要件定義](../12-system-development/12-1-システム-ソフトウェア-要件定義.md) と [12-2 設計](../12-system-development/12-2-設計.md) で扱う。

> **出題** UMLによる業務プロセスの可視化: H30午前I問23 ｜ UMLアクティビティ図: R4午前I問25

## 3. BPRとBPM

| 手法 | 内容 |
| --- | --- |
| **BPR**（ビジネスプロセス・リエンジニアリング） | **企業内の業務全体を対象として、業務プロセスを抜本的に見直すことによって、品質・コスト・スピードを改善し、競争優位性を確保すること** |
| **BPM**（ビジネスプロセス・マネジメント） | 業務プロセスを可視化し、**PDCAサイクルで継続的に改善する**こと |

**BPRは「抜本的な一度の変革」、BPMは「継続的な改善」**という違いがある。

BPRが「抜本的」であることには理由がある。既存の業務手順には、過去の制約（紙の帳票、組織の縦割り、通信手段の制限）に由来する部分が多く含まれている。制約がなくなっても手順だけが残っていることがある。**部分的な改善では、こうした前提そのものを問い直せない**。だから「ゼロから設計し直す」という発想をとる。

一方で、抜本的な変革は混乱も大きい。そこで、変革後の業務を**継続的に改善していく**仕組みとしてBPMが位置づけられる。

## 4. BPO

> **BPO**を説明したものはどれか。

答えは、

> **社内業務のうちコアビジネスでない事業に関わる業務の一部又は全部を、外部の専門的な企業に委託すること。**

別の設問では、

> **社内業務のうちコアビジネス以外の業務の一部又は全部を、情報システムと併せて外部に委託することによって、経営資源をコアビジネスに集中させること。**

と表現されている。

**BPO（Business Process Outsourcing）の眼目は「経営資源をコアビジネスに集中させる」**ことにある。単なるコスト削減ではない。経理、人事、コールセンタといった業務は、どの企業にも必要だが、それ自体が競争力の源泉になることは少ない。これらを専門企業に任せれば、**限られた人材と資金を、自社の強みを生むところへ振り向けられる**。

逆にいえば、**コアビジネスは外注してはならない**。[14-10 プロジェクトの調達](../14-project-management/14-10-プロジェクトの調達.md) で見た内外製分析と同じ判断である。中核を外に出せば、長期的に自社に知見が残らない。

誤答として並ぶものとの区別を押さえる。

| 記述 | 実際は何か |
| --- | --- |
| 業務全体を対象として業務プロセスを抜本的に見直し、品質・コスト・スピードを改善する | **BPR** |
| 災害や事故で被害を受けても重要事業を中断させない仕組みを構築する | **BCP**（→ [11-2 情報セキュリティ管理](../11-security/11-2-情報セキュリティ管理.md)） |
| 基準生産計画、部品表、在庫情報を基に資材の所要量と時期を求める | **MRP**（→ [21-2 エンジニアリングシステム](../21-business-and-industry/21-2-エンジニアリングシステム.md)） |
| プロジェクトを戦略適合性や費用対効果、リスクの観点から評価し、情報化投資のバランスを管理する | **ITポートフォリオ**（→ [17-1 情報システム戦略](17-1-情報システム戦略.md)） |

> **出題** BPO: H24午前I問23、R4午前I問23

## 5. RPA

> **RPA（Robotic Process Automation）**の説明はどれか。

答えは、

> **ホワイトカラーの単純な間接作業を、ルールエンジンや認知技術などを活用して代行するソフトウェア。**

**RPAの「ロボット」はソフトウェアであって、物理的な機械ではない**という点が決め手になる。誤答はすべて物理的なロボットや機器の説明である。

| 記述 | 実際は何か |
| --- | --- |
| **ホワイトカラーの単純な間接作業を代行するソフトウェア** | **RPA** |
| 自動制御によって対象物をつかみ、動かす機能をもつ産業用ロボット | 産業用ロボット（→ [21-2 エンジニアリングシステム](../21-business-and-industry/21-2-エンジニアリングシステム.md)） |
| 車両の状態や周囲の環境を認識し、自律的な走行を可能とするレーダ、GPS、カメラなどの機器 | 自動運転関連機器 |
| 人の生活空間で食事、清掃、移動などの生活支援に使用されるロボット | 生活支援ロボット |

RPAが対象とするのは、**定型的で、ルールが明確で、繰り返し発生する事務作業**である。システム間のデータ転記、帳票からの入力、定型レポートの作成などが典型例になる。

RPAが広がった背景には、**既存システムを改修せずに自動化できる**という事情がある。本来はシステム同士を連携させるのが筋だが、改修には費用と期間がかかり、他システムとの調整も要る。RPAは**人が画面を操作する手順をそのまま自動化する**ので、既存システムに手を入れずに済む。

ただしこれは弱点でもある。画面の配置が変われば動かなくなり、ロボットが増えれば管理が追いつかなくなる。**対症療法であって根本解決ではない**という認識をもって使う必要がある。

> **出題** RPA: R1午前I問28

## この章のまとめ

- 業務モデルの定義は**全体業務と情報の関連を整理し、情報システムのあるべき姿を明確化する**ことが目的。開発規模の見積りや構成要素の洗い出しは後の工程である。
- **論理モデルは経営目標から導いたあるべき姿**であり、現状を整理した現物モデルとは出発点が違う。両者の比較がギャップ分析。
- **UMLは複数の図法を目的に応じて使い分ける**。**業務フローの「分岐・並行処理・同期」を表すのはアクティビティ図**。
- **BPRは抜本的な一度の変革、BPMは継続的な改善**。
- **BPOの眼目は経営資源をコアビジネスに集中させること**。コアビジネスそのものは外注しない。
- **RPAのロボットはソフトウェア**。既存システムを改修せず自動化できる反面、画面変更に弱く、根本解決ではない。
